外挂服务器逆向还原方法论（通用 · 去标识版）

一句话：客户端只是半个系统。外挂能不能用、能用多久、什么时候被停，最终由它背后那台服务器决定。本文讲的是怎么把那台服务器「重新造出来」，并且造到能对账、能运维、能换版本。

适用范围：任意以「客户端 + 私有后台」形态分发的外挂套件。所有身份、域名、密钥、编号一律占位化；保留的只有流程、判据与失败形态。

第 0 章 总纲：从「外挂能用」到「服务器归我」

0.1 三条前提（不成立就别往下走）

外挂服务端可还原，本质依赖三件事。每条都要有实证动作，不能靠"应该是"：

前提内容实证动作（10 分钟内可做）不成立时的症状
A客户端把「能不能用」的判定交给了服务端断网启动、改 hosts 指向黑洞 IP、把 API_BASE 指到本地 mock，三次分别看哪些功能先死断网照样透视/自瞄 → 判定在本地，还原目标从"服务端"变成"客户端校验"（另一套方法论）
B协议可观测起代理抓一次登录，能看到请求体长度稳定且时间顺序可复现全程只有 TLS 握手成功、body 长度恒定极短 → 可能是 DNS/隐蔽信道，或走了驱动层隧道
C授权判定可被替代让 mock 返回一个自造的 MSG_LOGIN_OK，看客户端是否进入下一步 UI返回什么都停在原地 → 判定绑了签名/证书/时间/硬件，需要逐项拆
【判据】三条前提各自有实证动作。没有做过这三个实验就开始解协议，是最常见的白干两周。

前提 A 的实证方式（做法值得照抄，不需要照抄结论）

不要一上来抓包。先做减法：

  1. 全断网（禁用网卡）启动客户端 → 记录它停在哪一屏，报什么错。
  2. 通网但黑洞（API_BASE 指向 127.0.0.1:1）→ 记录它停在哪一屏。
  3. 通网但返回空 200（本地起一个只会回 200 + {} 的服务）→ 记录它停在哪一屏。

三次的停点差异就是信息量：

  • 三次都停在登录窗 → 授权在服务端，且登录是硬门（最理想）。
  • 断网停、黑洞不停 → 域名列表有本地兜底或离线缓存，注意"离线可用时长"字段。
  • 三次都进得去、功能却全都失效 → 授权只是软门，真正的门在 CFG_BLOB 里（见第 7 章）。

前提 C 的形状（最关键的一段）

「可被替代」不等于「返回 true 就行」。它通常有三个附着点，必须逐个识别：

附着点形态判别方法
签名响应带 sign 字段，客户端本地验改 body 不改 sign → 客户端报"数据异常"而非"授权失败"
时间响应带 expire / server_ts，客户端比对本地时间把 expire 改成过去 → 立即失效，说明时间被采信
硬件响应回显 HWID，客户端与本地指纹比对回显错一个字节 → 提示"设备异常"

【反例】曾把一个登录响应整体照抄，只把 code 从 1001 改成 0，客户端弹出"授权成功"却在 3 秒后自动退出。原因：expire 字段仍是旧值（已过期），客户端在拿到 MSG_LOGIN_OK 后立刻做了一次本地到期校验。教训："成功"这个消息本身也带状态，不能只改结果码。

0.2 成功判据五档（报进度只能报档，不能报"差不多了"）

档名称唯一判据典型假成功
D0能连服务端日志出现来自客户端的完整请求行 + 请求体抓到自己代理的请求，但客户端并未真正发出（代理空转）
D1能登录客户端离开登录窗，进入主界面UI 只是隐藏了登录框（热键/参数跳过）
D2token 被接受后续至少两个端点用该 token 返回业务数据（非"授权失败"）一个端点放行、其余全拒（token 只是本地字符串）
D3配置被接受客户端把 CFG_BLOB 应用后，功能下游产物真的变了（画面/状态/日志）返回 200、长度对、内容错，客户端静默丢弃
D4账本自洽同一卡密连续心跳 N 次，剩余时间单调递减且与真实时长一致（误差 <2%）扣时发生在登录而不在心跳 → 断线不扣，账目虚高
D5可运维换 CLIENT_VER、换 CHANNEL、踢人、灰度回滚各跑一遍不炸单版本能跑，换一版全崩
【判据】任何"还原完成"的说法必须落到 D3 以上。D1/D2 属于"界面过了"，是最容易自我欺骗的两档。

0.3 四层可交付（卡住时按层排查，不要跳层）

层内容判断"这层做完了"
契约层端点表、字段映射、错误码字典任一抓包能 100% 落到某个端点与字段，未命名字段占比 <20% 且有清单
状态层会话、卡密、剩余时间、顶号、指令队列重启服务端后，客户端无需重新登录仍能继续（或明确会断，且断得符合预期）
数据层CFG_BLOB 生成、OFFSETS_TABLE 版本化、更新包分发客户端接受你的配置并功能生效；换一版客户端能生成对应代次
运维层多域名、证书、健康检查、监控、回滚主域名拔掉，备用域名 30 秒内接上；灰度开关一改即生效

【反例】一个团队把契约层做到 95%，状态层完全空缺：登录成功、配置下发成功、功能也生效，但每次重启服务端所有在线用户全部掉线且被扣满一小时。用户投诉"掉线扣时"，最后不是协议问题，是状态层没做持久化。

0.4 三种走法，先选路再动手

走法做法适用判据死法
A 全量重写自己实现全部端点，客户端只认你的服务器端点 ≤ 30 且状态字段少；能拿到全部 CFG_BLOB 生成逻辑端点其实更多（藏在更新包里）；漏一个冷门端点导致某功能永久灰掉
B 差分代理中间人转发到上游真服，只改写必要字段上游仍可用；你只需要改授权/时间/配置上游一改协议全崩；TLS pinning 让你无法中间人
C 录音回放先录下全部真实响应，按请求指纹回放只要"先跑起来"，用来做客户端行为观察回放态永远无法处理"第一次见到的请求"；时间字段过期后集体失效

推荐顺序：C → A，跳过 B。 理由：B 依赖上游存活，而你做这件事的前提通常正是上游不可用/不可控；C 用来学习客户端如何消费响应（第 9 章的假成功识别必须在 C 态做），A 才是交付物。

【判据】选路的唯一硬指标：你能不能自己产出 CFG_BLOB。能 → 走 A；不能 → 先 C 观察，把 CFG_BLOB 的内部 schema 反推出来再谈 A。

0.5 本章要点

  1. 三条前提各有实证动作，10 分钟能做完，先做再加。
  2. 授权有三附着点（签名/时间/硬件），改结果码不等于改授权。
  3. 进度只报 D0–D5 五档，D3 以下不算还原。
  4. 走法按「能否自产 CFG_BLOB」选，不要按"哪个听起来快"选。

L1驱动/内核模块.sys、内核回调、IOCTL 面驱动加载日志、sc query、签名信息多数不碰（见 2.5）
L2注入与游戏交互手动映射的 DLL、hook 表、OFFSETS_TABLE 消费者进程模块列表、内存扫描、功能开关要碰：配置正确性在这里被消费
L3业务 UI登录窗、卡密输入、到期提示、公告窗口枚举、控件文本、热键要碰：它是"用户可见的判定结果"
L4网络层域名列表、加密/签名、重试与轮询抓包、代理、hook send/recv核心战场
L5服务端授权、配置、更新、心跳、指令、统计、卡盟只能从 L4 侧反推 + 差分实验交付物

填表要求：每一层都要写出具体文件名/进程名/端口号（脱敏后写进你的私有笔记，不进本文）。填不满的格子，就是你接下来两天的作业。

1.2 授权闸门到底装在哪一层：三个候选位置

外挂的"门"不止一道。绝大多数还原失败，是把软门当成硬门，或反之：

位置形态打桩方式过了它的现象
登录前门卡密 → SESSION_TOKENmock 登录端点返回合法 token离开登录窗
配置后门CFG_BLOB 内带 license 字段 / 水印 / 有效期改写 blob 内该字段后重新加密功能从灰变亮
注入前门驱动加载前校验时间/签名/白名单打桩时间源、伪造返回码注入模块被加载（模块列表出现 CHEAT_CORE）
【判据】判别"门在哪一层"的唯一可靠方法：逐层打桩，看功能在哪一层开始可用。三层都打桩才可用 → 三道门都在；只有第一层打桩就可用 → 后两道是软门（往往是营销话术而非技术门）。

1.3 一次完整会话的时序（照这个顺序摆你的实验）

[T+0.0s]  L0 启动器拉起 CHEAT_CORE（或先加载驱动）
[T+0.3s]  L4 读本地域名列表 → 选第一个可用 API_BASE
[T+0.5s]  L4 POST /auth/login   {LICENSE_KEY, HWID, CLIENT_VER, REPLAY_TS, NONCE, sign}
[T+0.9s]  L5 → MSG_LOGIN_OK {SESSION_TOKEN, expire, cfg_ver, notice, ver_new}
[T+1.0s]  L3 关闭登录窗，读 cfg_ver
[T+1.1s]  L4 GET  /cfg/CFG_BLOB?ver=…&token=…
[T+1.4s]  L5 → CFG_BLOB（编码→压缩→加密）
[T+1.5s]  L2 解包 → 应用 OFFSETS_TABLE → 等待游戏窗口
[T+2.0s]  L0 检查 ver_new → 若 force=1 则强制更新（此时功能尚未注入）
[T+2.5s]  L2 注入宿主 → hook 生效
[T+60s ]  L4 POST /auth/beat {token, HWID, REPLAY_TS} → MSG_HEARTBEAT_ACK {remain}
[T+…  ]  L5 可随时下发 MSG_FORCE_LOGOUT / MSG_UPDATE_AVAIL

这张时序图有三个用途：① 决定你的实验顺序（必须先让 T+0.5 成立，否则后面全是空跑）；② 决定你的假成功判据（T+1.5 才是"配置生效"点）；③ 决定你的日志字段（每个 T 都要有一条可对齐的日志）。

2.5 驱动与内核模块：多数时候你不需要碰它

外挂的驱动通常干三件事：读宿主内存、隐藏自身、绕过检测。它与"服务器还原"的交集只有两处：

  1. 加载期校验：驱动加载前可能要求一个"授权通过的凭据"（注册表项/文件/命名管道）。这个凭据由服务端下发 → 你要能生成它（见第 6 章）。
  2. 网络隧道：极少数套件把心跳走驱动层（NDIS 过滤/自定义协议），此时常规代理看不到，必须用驱动层或物理层抓包。

判别法：

# 驱动是否存在、签名者是谁、加载方式
Get-ChildItem C:\Windows\System32\drivers\*.sys | Where-Object { $_.LastWriteTime -gt (Get-Date).AddDays(-90) } |
  Select-Object Name,LastWriteTime,Length
Get-AuthenticodeSignature .\CHEAT_CORE.sys | Format-List Status,SignerCertificate
sc.exe qc <SERVICE_NAME>          # 服务注册信息（启动类型、binPath）
【判据】驱动不是你的交付物。只有当"服务端必须产出一个让驱动接受的东西"时，才需要深入它；否则把它当作黑盒，只观测它的输入输出。

2.6 静态的边界：三件永远看不到的事

看不到为什么只能怎么拿
服务端逻辑代码不在样本里差分实验（第 5/6 章）：改一个输入，看输出怎么变
动态密钥运行期协商或与 HWID 绑定运行期 hook 取（第 3/4 章）
远端灰度服务端按 CHANNEL/HWID 分流多账号/多版本对拍（第 7 章）

写进文档的规矩：静态能得出的结论，必须标注【静态】并写清代次；凡是"我猜服务端会……"的句子，一律改写成待验假设 + 验证动作。

2.7 本章要点

  1. 代次冻结三件套（哈希/时间/版本），缺一件结论会漂。
  2. 三层静态入口各有盲区，磁盘上没有的东西先去内存看。
  3. 壳分诊的目的是"能不能读到字符串"，不是"脱得多干净"。
  4. 域名表六种存法，逐种有判别法；解出来必须能自证。
  5. 驱动多数时候是黑盒；只关心它要什么凭据。

3.5 时钟与延迟：三个钟，只有一个能用

钟来源可信度用途
本地系统钟用户机器低（用户可改，REPLAY_TS 就取它）只用来满足"时间戳窗口"
服务端钟响应里的 server_ts高用来校本地漂移、判定"时间加速"攻击
抓包主机钟抓包工具中（含捕获延迟）只用来算间隔与顺序

延迟补偿的做法：不要用"精确时刻"配对请求与响应，用配对率随 Δt 的曲线——把 Δt 从 0 扫到 3000ms，取配对率峰值所在的窗口，这个窗口就是你的"经验延迟"。写文档时写"Δt∈[x,y] 时配对率 >90%"，不要写"延迟约 80ms"。

【判据】凡是拿"时间"当判据的地方（扣时、到期、心跳间隔），必须写明用的是哪个钟，否则跨机器复现时结论必然打架。

3.6 本章要点

  1. 拦截层先 d 后 a，最后 e；选层的目的是"能看见什么"，不是"哪个高级"。
  2. pinning 的判据是"握手成功但请求不到"，不是"报网络异常"。
  3. 端点表三个易漏字段：CLIENT_VER、CHANNEL、sign。
  4. 备用域名的存在性比内容重要；它常跟更新包同代。
  5. 时间判据必须绑定钟，延迟用窗口不用点。

4.1 算法指纹：不看函数名，看常量与结构

4.2 密钥从哪来：四种形态，各有识别法

形态特征识别对你的影响

派生不同卡密/不同账号解出的密钥不同用两个账号对拍，密钥不同 → 派生于 LICENSE_KEY/HWID/SIG_KEY必须复刻 KDF（通常是 md5(盐 + 卡密)[:16] 一类）

会话协商首次连接有一段"握手报文"，之后密文变前 2–3 个报文长度固定且非业务少见；多为"客户端随机数 + 服务端公钥加密"的简化版

派生形态的 KDF 反推（最小可跑模板）：

import hashlib, itertools, base64
KEY_LEN = {16:'aes128', 32:'aes256', 24:'3des'}
def cands(license_key, hwid, ver, salt_guesses):
    parts = {'L':license_key, 'H':hwid, 'V':str(ver), 'C':'CHANNEL'}
    for order in itertools.permutations('LHV', 3):
        for sep in ['', '|', ':', '-']:
            base = sep.join(parts[k] for k in order)
            for salt in salt_guesses:
                for algo in ('md5','sha1','sha256'):
                    h = getattr(hashlib, algo)((salt + base).encode()).hexdigest()
                    for enc in (h, base64.b64encode(bytes.fromhex(h)).decode()):
                        yield f'{algo}({salt}+{order}{sep!r})', enc[:32]
# 判据：能把已知密文解开成合法 JSON/已知明文 的那一条
【反例】花两天枚举 KDF 变体，最后发现密钥就是服务端下发的、且它本身用固定密钥加密（SIG_KEY）。教训：先用"服务端下发"假设试一次（把登录响应里每个可疑字段当密钥逐个试解），再用"派生"假设。顺序反了会白烧两天。

4.3 层次顺序：六种排列，用"长度 + 魔数"五分钟判掉

#排列判别
1明文 → AES → base64解 base64 得 16 倍数；AES 解出即为明文
2明文 → gzip → AES → base64AES 解出后头两字节 1F 8B
3明文 → AES → gzip → base64解 base64 后头两字节 1F 8B（压缩在最外）
4明文 → XOR → base64base64 解出等长；异或后可读
5明文 → RC4 → hexhex 解出等长；RC4 解出可读
6明文 → 自研打包(head+len+payload) → AES头里带 len/ver/crc，payload 才是 AES 密文

判掉顺序的固定流程（照做，别跳）：

  1. 取密文，先看外层编码：字符集是 base64/hex 就先解码，得到二进制 X。
  2. 看 X 的前 2–4 字节：1F8B/789C → 压缩在外层；MZ/PK → 没加密；否则当密文。
  3. 如果压缩在外层，先解压再回第 2 步（可能套了两层压缩）。
  4. 剩下真是密文的，按 4.1 的指纹判算法，按 4.2 定密钥，解出来的东西必须能自证（JSON/MZ/OFFSETS_TABLE 的固定头）。

4.4 签名：拼接顺序是唯一难点

签名的形式通常是 sign = H(拼接串 + SIG_KEY)，难点全在拼接串怎么拼。用字段参与测试逐项排除，比猜快得多：

实验改动观察结论

E3调整 JSON 字段顺序（不改值）sign 不变 → 服务端按键名排序拼接拼接前排序

自动验证候选拼接（枚举 + 已知 pair，几秒出结果）：

import hashlib, itertools, json
def gen(body: dict, sig_key: str):
    items = [(k, str(v)) for k, v in body.items() if k not in ('sign',)]
    seps = ['', '&', '|', ',']
    for sep in seps:
        for sort in (True, False):
            seq = sorted(items) if sort else items
            for kv in ('k=v', 'v', 'k:v'):
                s = sep.join(f'{k}={v}' if kv=='k=v' else (v if kv=='v' else f'{k}:{v}') for k,v in seq)
                for suffix in (sig_key, sig_key.lower(), sig_key.upper()):
                    for algo in ('md5','sha1','sha256'):
                        for form in ('hex','HEX'):
                            h = getattr(hashlib, algo)((s + suffix).encode()).hexdigest()
                            yield (algo, sep, sort, kv, form), (h if form=='hex' else h.upper())
# 用一条已知 (body, sign) 对拍，命中即停
【判据】签名算法的验证判据只有一个：用已知抓包的 (body, sign) 能算出同一个值。算不出来就说明拼接/编码/密钥任一不对，不要先去做"服务端也许不验签"的假设——验不验签要用 E6（改 body 不改 sign）单独测。

你的服务端要不要实现 nonce 表？判据：客户端自己是否会生成 nonce。若客户端每次请求的 nonce 都不同（含随机数），说明它期待服务端校验；若它复用同一个值，说明服务端根本没验。照客户端的期待实现，不要照你的喜好实现——多实现一层校验，唯一的后果是把自己的测试卡死。

  1. 算法靠指纹（常量/结构/长度）判，不靠函数名。

步做什么产出

2 查在字符串表、错误提示、日志文案里找同名/近义词语义候选清单
3 投票多份抓包（多账号、多版本）看该字段的变化规律，与候选逐一比对定名或标"未命名"
# 步 1 的最小统计：每个字段的取值分布
Get-Content .\CAP_FILE.responses.jsonl | ForEach-Object { ($_|ConvertFrom-Json).body } |
  ForEach-Object { $_.PSObject.Properties | ForEach-Object { [pscustomobject]@{k=$_.Name; v=[string]$_.Value} } } |
  Group-Object k | ForEach-Object {
    $vals = $_.Group.v | Sort-Object -Unique
    [pscustomobject]@{ field=$_.Name; n=$_.Count; uniq=$vals.Count; sample=($vals | Select-Object -First 3) -join ' | ' }

判据：uniq=1 的字段是常量（版本号/渠道/固定 key）；uniq≈n 且长度固定的十六进制是哈希/ID；递增整数是时间或计数；长度为 16/24/32 的 base64 是加密体。

【反例】把一个 uniq=2 的字段命名为 is_vip，结果是 code（0/1001 两个取值）。教训：字段名不是语义，取值分布才是。

6.2 扣时发生在哪：五个候选点，用三个实验定死

候选点判别实验结果解读
登录时扣登录后立刻断网 10 分钟，再登录看 remain少了 10 分钟 → 登录时不扣，或扣了又补
心跳时扣登录后正常心跳 10 分钟，不发任何业务请求remain 少 10 分钟 → 扣时在心跳
退出时扣登录→正常退出→再登录若"退出"才扣，则崩溃/断电会白嫖
拉配置时扣只登录不拉配置时间不动 → 与配置无关
指令/动作时扣只发心跳不触发功能时间不动 → 与业务无关

典型实测形态（多数套件）：扣时 = 每次心跳按"距上次心跳的秒数"累加。这条形态有三个可验证推论：

  1. 心跳间隔越长，误差越大（间隔 60s 时误差上限 60s/次）。
  2. 客户端崩了不回心跳 → 不扣时（对用户有利，对你是漏洞）。
  3. 服务端重启丢了 last_beat → 可能多扣（用服务端当前时间 − 旧 last_beat）。

【判据】写进文档时必须写清："扣时发生在 X，粒度 Y 秒，断线保底 Z"。三者缺一个，后面所有对账都做不了。

断线保底的正确实现

-- 每次心跳：只累加"有上限"的增量，避免服务端停机导致的巨额扣时
UPDATE license
   SET remain_sec = CASE
         WHEN remain_sec IS NULL THEN remain_sec
         WHEN :now - last_beat > :max_gap THEN remain_sec - :max_gap   -- 上限（如 180s）
         ELSE remain_sec - (:now - last_beat)
       END,
       last_beat = :now,
       session_id = :sid
 WHERE license_key = :key AND frozen = 0 AND banned = 0;

6.3 顶号、并发与心跳租约

策略现象实现要点
单会话（后踢前）第二端登录成功，第一端 ≤1 个心跳周期后被踢用 session_id 比对，不一致就回 MSG_FORCE_LOGOUT
多会话（限 N）第 N+1 端被拒会话表 + 计数
无限制同卡多人共用多半是上游本身就烂；你实现时要决定是否收紧

踢人的延迟 = 心跳间隔，这一点必须写进验收：用户感知的"顶号速度"不是由你的逻辑决定，而是由客户端的轮询周期决定。若客户端只在心跳里检查 session_id，你的服务端无法做到"秒踢"，除非它还有长连接推送。

【反例】为了让"顶号即时生效"，把心跳间隔从 60s 改成 5s，结果一晚上把服务端打挂（在线 2000 人 × 12 次/分 = 400 QPS 的纯心跳）。教训：踢人延迟是产品决策，不是技术优化点。

6.4 设备绑定：HWID 的组成与更换配额

组成项稳定性采集方式（客户端侧）还原时要不要复刻
MachineGuid高（重装系统才变）注册表 Cryptography\MachineGuid要：多数套件用它做主键
硬盘序列号 / 卷序列号中（换盘就变）WMI / IOCTL_STORAGE_QUERY_PROPERTY看情况
主板序列号高WMI Win32_BaseBoard少数用
网卡 MAC低（虚拟网卡多）GetAdaptersInfo慎用：多网卡会抖动
CPUID / 处理器特征高cpuid少数用
用户名 / 计算机名极低环境变量只会做辅助校验

还原要点：你的服务端不需要自己算 HWID——它是客户端算好传来的。你要做的是：

  1. 判断它是否稳定：同一台机器连登 3 次，HWID 是否完全一致（有套件每次取 MAC 顺序不同导致抖动 → 你必须做"模糊匹配"或多值容忍）。
  2. 实现更换配额：hwid_changes < max 时允许改绑，超过就拒。
  3. 处理冲突：同一 HWID 绑多张卡（正常，网吧/多开），同一张卡绑多个 HWID（异常）。
-- 改绑：只允许在配额内，且记录审计
UPDATE license SET hwid = :new, hwid_changes = hwid_changes + 1
 WHERE license_key = :key AND hwid_changes < :max_changes;
-- 影响行数 0 ⇒ 拒（配额用完），必须给客户端明确的 code，不要给"未知错误"

6.5 状态机：把卡的一生画成图

[未激活] --首次登录/激活--> [使用中] --expire--> [已到期]
     |                          |  |
     |                          |  +--frozen=1--> [冻结] --解冻--> [使用中]
     |                          +--banned=1--> [封禁]（终态，除非人工解封）
     +--兑换码已用--> [作废]
[已到期] --续费/加时--> [使用中]
[使用中] --退款--> [已退款]（终态，remain 归零，审计留痕）

每个迁移必须回答三件事：谁能触发、触发时改哪些字段、客户端怎么知道（哪个 code / 哪个消息）。三件事没写清的迁移，实现出来一定有状态漏网。

6.6 对账：让账本自己说话

对账公式（缺一项就对不平）：

发卡总量 = 未激活 + 使用中 + 已到期 + 冻结 + 封禁 + 退款 + 作废 + 损耗
其中「损耗」= 已发未售（代理囤货） + 测试卡 + 补发卡
-- 按批次对账
SELECT batch_id,
       COUNT(*)                                            AS issued,
       SUM(CASE WHEN start_ts IS NULL THEN 1 ELSE 0 END)    AS never_activated,
       SUM(CASE WHEN banned=1 THEN 1 ELSE 0 END)            AS banned,
       SUM(CASE WHEN refunded=1 THEN 1 ELSE 0 END)          AS refunded,
       SUM(CASE WHEN start_ts IS NOT NULL AND expire_ts < :now AND refunded=0 AND banned=0
                THEN 1 ELSE 0 END)                          AS expired,
       SUM(CASE WHEN start_ts IS NOT NULL AND expire_ts >= :now AND frozen=0 AND banned=0
                THEN 1 ELSE 0 END)                          AS active
  FROM license GROUP BY batch_id;
【判据】对账的唯一通过标准：上面所有分项之和 = 发卡总量，误差 0。差 1 张也要查——通常是一张卡在"激活中"被打断（写了 start_ts，没写 expire_ts），这类半成品卡会在两周后变成用户投诉。

6.7 本章要点

  1. 卡密分六类，混着建模必然对不上账。
  2. 扣时点用三个实验定死，且必须写"粒度 + 断线保底"。
  3. 踢人延迟由客户端心跳周期决定，不要用缩短间隔去"优化"。
  4. HWID 由客户端算，服务端只负责稳定性容忍、配额与冲突。
  5. 状态机每个迁移答三问；对账必须分项求和为零。

第 7 章 配置与更新下发：CFG_BLOB 与 OFFSETS_TABLE

7.1 CFG_BLOB 的解剖：四层，每层都有判据

[外层] base64 文本（或 hex）
  └─ [第2层] gzip/zlib 压缩体（1F 8B / 78 9C）
       └─ [第3层] AES-CBC 密文（16 字节对齐，前 16 字节常为 IV）
            └─ [第4层] 内层结构：JSON / TLV / protobuf
                 ├─ ver          配置代次
                 ├─ game_ver     适配的宿主版本（关键！）
                 ├─ offsets[]    OFFSETS_TABLE
                 ├─ features{}   功能开关与参数
                 ├─ notice       公告文本
                 └─ sig          内层签名（有的套件有）

逐层剥离的固定流程：解 base64 → 看头 2 字节（压缩则解压）→ 看长度是否 16 的倍数（是则 AES）→ 解密后看是否可 JSON 解析 → 不可解析则按 TLV 猜（先看前 4 字节是不是长度）。

现象说明处置
解到第 3 层就"看起来像随机"IV 不是前 16 字节，或 CBC 改成 CTR换模式试（CBC/CTR/CFB 各一遍，判据是内层可解析）
内层是 TLV前 4 字节 len、后跟 tag按 (len,tag,payload) 循环解
内层能解析但字段对不上有字段级加密（个别敏感字段单独 AES）单字段试解，通常密钥同源
每次取到的 blob 不同但 ver 相同有随机盐/时间戳参与加密解密时要取同一份盐，别用旧盐解新包
【判据】CFG_BLOB 是否"用对了"只有一个判据：客户端应用后，某个功能的下游产物发生变化（画面/状态/日志）。长度对、哈希对、能解压——都不算。

7.2 OFFSETS_TABLE：偏移表与客户端版本的同代约束

偏移表是外挂的"弹药"，它必须与宿主版本严格同代。典型结构：

{"ver": 114, "game_ver": "1.2.3.4",
 "offsets": [
   {"name":"LOCAL_PLAYER","module":"game.exe","pattern":"48 8B 05 ?? ?? ?? ?? 48 85 C0","rva":"0x1A2B3C4","type":"ptr"},
   {"name":"VIEW_MATRIX","module":"game.exe","pattern":"F3 0F 10 05 ?? ?? ?? ??","rva":"0x2C4D5E6","type":"mat4"}
 ]}
约束内容违反后的现象
同代game_ver 必须等于宿主真实版本功能全灰 / 读到垃圾值 → 崩溃
特征码自校验客户端可能用 pattern 去内存里重新定位，定位失败就放弃该条部分功能失效（不是全失效，很容易被误判为"某个功能坏了"）
长度/类型一致type 决定读几个字节、怎么解释数值离谱（血量为 0、坐标 NaN）
名字不可乱改客户端按 name 索引改了名字 → 该条被忽略

生成偏移表的三条纪律：

  1. 不要手搓 RVA：用特征码定位 + 基址重算，RVA 只是缓存，pattern 才是真身。
  2. 每条都要有"这条没生效"的独立可观测信号（见 9.1），否则你无法知道 100 条里坏了几条。
  3. 保留上一代：game_ver 一变，先发一份 ver+1 但 features 全关的"安全包"，确认客户端能接受，再逐条开。

7.3 版本协商与强制更新：三个字段谁说话

外挂的更新判定常见三个字段，它们互相打架是常态：

字段语义（猜测）判别方法
ver_new最新版本号改大 → 若弹更新提示，说明它被读
force是否强制置 1 → 若不点更新就进不去，说明强制生效；若只是提示，说明它被忽略
min_ver最低可运行版本把客户端 CLIENT_VER 改成低于它 → 若被拒，说明服务端用它在判
# 三字段正交实验（每次只改一个，其余保持上游原值）
# A: ver_new += 1              → 观察：提示？可跳过？
# B: force = 1                 → 观察：能否绕过？绕过后功能是否受限？
# C: CLIENT_VER = 低于 min_ver → 观察：拒绝文案与 code
【反例】只测了 force=1 发现"能跳过"，就断言"更新不是硬门"，结果线上换版本后所有用户卡在"请更新"。原因：真正的门是 min_ver，force 只是 UI 提示位。教训：三字段要正交测，别用单个实验下全局结论。

7.4 灰度与回滚：键的设计决定你能不能救火

灰度键优点缺点
CHANNEL实现最简单，改配置即生效粒度太粗，出事影响整渠道
HWID 哈希取模可分 5%/10%/50%用户不可控，测试者可能抽不到
白名单（卡密/HWID）可精确指定测试用户需要维护名单
卡密批次 batch_id适合"只对新批次生效"老用户永远在旧配置

回滚的正确形态：不是"把配置改回去"，而是把 cfg_ver 指针指回上一版（配置一旦下发就被缓存，改内容没用，改指针才有效）。

cfg_release(cfg_ver, game_ver, blob_sha256, sig, created_at, active)
-- 回滚 = UPDATE cfg_release SET active=0 WHERE cfg_ver=:bad; UPDATE ... SET active=1 WHERE cfg_ver=:good;
【判据】回滚演练的唯一判据：拿一台已知会崩的客户端，回滚后它能正常进游戏。没有这个演练，你的"回滚方案"只是文档。

7.5 分发：CDN、对象存储与缓存头

方式配置注意
对象存储直链CFG_BLOB 放 OSS/S3，签名 URLURL 有效期要 > 客户端重试窗口
CDN前置 CDN，回源对象存储缓存键必须含 cfg_ver，否则回滚时命中旧缓存
自建自己的 nginx需要 Range 支持（更新包断点续传）

必须设置的响应头：

Cache-Control: public, max-age=300, must-revalidate   # 配置类：短缓存
ETag / If-None-Match                                  # 让客户端能 304
Content-Length                                        # 缺了会导致客户端截断（静默失败）
【反例】配置类资源设了 max-age=86400，回滚后 24 小时内客户端仍拿旧包，表现为"回滚了但没人恢复"。教训：配置类缓存 ≤5 分钟，且缓存键必须含版本。

7.6 校验与降级：签名失败时客户端会干什么

客户端行为判别你的实现要求
静默丢弃，保留旧配置功能仍是旧行为你必须保证"新旧都可用"，否则一次坏包 = 全体停摆
报错退出弹窗 + 退出你的验证必须先于发布做（离线自测）
降级到内置默认功能部分可用你要知道"默认值是什么"，别把它当成功

永不返回半份配置的工程要求：生成 → 校验（自解一遍）→ 签名 → 存档 → 再发布。四步里任何一步失败，都不许把文件推到线上。

7.7 本章要点

  1. CFG_BLOB 四层，逐层剥离有固定流程；能解析不算成功，功能生效才算。
  2. OFFSETS_TABLE 与 game_ver 同代，pattern 才是真身，且每条要有独立信号。
  3. 更新的三个字段要正交测，min_ver 常是真门。
  4. 回滚是"改指针"，不是"改内容"；缓存键必须含版本。
  5. 生成→自校验→签名→存档→发布，缺一步就可能全体停摆。

第 8 章 心跳、在线态与远程指令

8.1 心跳的三个作用：一个请求，三份语义

作用表现你的实现要点
保活停发心跳 → 服务端判离线 → 顶号/配额释放TTL 必须大 > 心跳间隔 × 2，否则误判离线
扣时remain 递减增量要设上限（6.2 的 SQL）
配置版本核对响应里带 cfg_ver / ver_new，客户端据此决定是否重拉你的 cfg_ver 一改，客户端要在 ≤1 个周期内跟着变

间隔来源：不要假设 60s。抓包量一下实测间隔，并写出分布（有的套件首次 10s、稳定后 300s）。判据：连续 10 次心跳的间隔中位数，而不是某一次的间隔。

# 从落盘记录算心跳间隔分布
$t = Get-Content .\CAP_FILE.requests.jsonl | ForEach-Object { $_ | ConvertFrom-Json } |
     Where-Object { $_.ep -eq '/auth/beat' } | ForEach-Object { [datetime]$_.t }
$d = 1..($t.Count-1) | ForEach-Object { ($t[$_] - $t[$_-1]).TotalSeconds }
$d | Measure-Object -Average -Minimum -Maximum
($d | Sort-Object)[[int]($d.Count/2)]      # 中位数

8.2 超时与离线判定：两套判定会打架

判定方依据结果
服务端now - last_beat > TTL清理会话、释放并发额度、可被新登录顶掉
客户端自己收到的最后响应时间弹"网络异常"、重连、或继续用缓存

两者不一致时的典型症状：服务端认为你离线了，客户端还在用旧 token 发心跳 → 心跳返回"未登录" → 客户端不会自动重新登录 → 用户看到"功能还在但什么都不生效"。

处置办法：给"token 失效但客户端仍在跑"设计一个专用的错误码，并通过心跳响应把它带出去；不要用"网络异常"糊过去（客户端会一直重试，永远不重新登录）。

beat → 200 {"code":1009,"reason":"session_gone"}   # 客户端据此重新走 login
【判据】离线判定的正确性判据：拔网线 5 分钟再插上，看客户端是否自动恢复。若它原地不动，说明你的 session_gone 分支没实现，或 code 用错了。

8.3 强制下线与踢人：幂等是唯一难点

场景你的动作幂等要求
顶号旧会话下次心跳返回 MSG_FORCE_LOGOUT连续 3 次心跳都返回同一结论，不能第 2 次变成"成功"
封禁立即返回封禁码 + 拒绝所有端点封禁后已发的配置仍可下载？由你决定，但要一致
冻结允许登录但功能不可用 / 直接拒与 6.5 状态机一致
到期返回到期码到期后仍允许心跳（用于展示"剩余 0"），但不允许拉配置

补偿规则（用户最容易投诉的地方）：

  • 因服务端故障导致的掉线，不扣时（用 6.2 的 max_gap 天然实现）。
  • 因顶号导致的被动下线，不额外扣时。
  • 因封禁不退时间（写明规则，别在代码里随机）。

8.4 指令队列：拉取式与推送式

形态实现延迟适用
拉取式客户端每次心跳问"有没有指令"≤1 个心跳周期绝大多数套件
推送式客户端保持长连接（WS/自定义 TCP）秒级少数，且实现更重

拉取式的表结构（最小可用）：

CREATE TABLE cmd (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  license_key  TEXT NOT NULL,
  kind         TEXT NOT NULL,      -- FORCE_LOGOUT / UPDATE_AVAIL / CLEAR_CFG / NOTICE
  payload      TEXT,
  created_at   INTEGER NOT NULL,
  delivered_at INTEGER,            -- 第一次被取走
  acked_at     INTEGER,            -- 客户端确认
  expire_at    INTEGER             -- 过期作废，避免"三天后突然弹旧公告"
);
CREATE INDEX idx_cmd_pending ON cmd(license_key) WHERE acked_at IS NULL;

三条纪律：

  1. 指令必须有 id，客户端要能确认（ack），否则你会重复投递到用户崩溃。
  2. 投递即标记，但确认才删除；未确认的按 expire_at 自然过期，不要无限重投。
  3. FORCE_LOGOUT 必须与 8.3 的顶号逻辑共用同一套判定，否则会出现"心跳说踢、指令说别踢"。
【反例】指令表只按 license_key 删，不按 id 删：用户开两个客户端，一个 ack 了就把另一个的指令一起清了，表现为"有时候能收到踢人，有时候收不到"。

8.5 时钟漂移与"时间加速"：自建侧必须处理的三件事

攻击面现象你的处置
改系统时间客户端本地时间跳到明天，expire 立即到期或永不到期以服务端 server_ts 为准下发，客户端本地只做展示
时间加速（变速齿轮）客户端内部计时被压缩，心跳变密服务端按到达时刻计账，不信客户端自报的间隔
时区/夏令时跨时区用户的到期时刻错 1 小时全链路用 UTC 秒，展示层再转本地时区
-- 计账只用服务端时间，且用"单调"来源（避免 NTP 回拨导致的负增量）
UPDATE license SET remain_sec = remain_sec - MAX(0, MIN(:now - last_beat, :max_gap))
 WHERE license_key = :key;

8.6 本章要点

  1. 心跳一个请求三份语义，TTL 必须 > 2× 间隔。
  2. 服务端与客户端两套离线判定会打架，用专用 code 收敛。
  3. 踢人必须幂等，补偿规则要写死。
  4. 指令要 id + ack + 过期，投递与删除分离。
  5. 计账只信服务端时钟，且增量取 MAX(0, …)。

第 9 章 客户端副产物：服务端必须产出「真能用」的数据

9.1 偏移表/特征码：正确性只能用下游产物判

下游产物怎么观测判据强度
画面变化截图对比（同一场景、同一视角）强
状态数值宿主内存里的目标值（血量/坐标）强
客户端日志CHEAT_CORE 自己打的"应用配置成功/失败"中（可能骗人）
界面状态功能开关从灰变亮弱（最常见假成功）
HTTP 200服务端返回成功不算判据

最小验证切片（一次只验一条）：

① 只下发 1 条 offset（比如 LOCAL_PLAYER），features 全关
② 判定：客户端日志出现 "offset LOCAL_PLAYER ok" 且 内存读到的指针非空
③ 再加 1 条（VIEW_MATRIX），判定：截图视角矩阵变化
④ 两条都对，再批量下发
【判据】"偏移表可用"的唯一判据：至少一条 offset 能被客户端独立验证通过。100 条里有 99 条坏、1 条好，和 100 条全坏，在客户端表现上完全一样（都是"功能不亮"）。

9.2 假成功的四种形态（每一种都真实发生过）

形态表象根因检出方法
空 body 型HTTP 200，Content-Length: 0服务端分支漏了/异常被吞断言 body_len > 0 且能解析
结构对内容错JSON 合法、字段齐全、值全是 0默认值被当成真实值返回拿一个"已知非零"的场景对比
版本错配ver 对、game_ver 不对拿了旧的偏移表在客户端日志里核对 game_ver
被客户端 CRC 拒客户端"看起来很满意"，但功能不生效客户端对 blob 有内部校验（长度/CRC/字段数）逐字节对比上游真包，找差异字段
# 快速体检：把所有响应按"长度=0 / 解析失败 / 全零字段"分桶
Get-Content .\CAP_FILE.responses.jsonl | ForEach-Object {
  $o = $_ | ConvertFrom-Json
  $len = if ($o.body_raw) { $o.body_raw.Length } else { 0 }
  $ok  = $null -ne $o.body
  [pscustomobject]@{ ep=$o.ep; len=$len; parsed=$ok }
} | Group-Object ep | ForEach-Object {
  [pscustomobject]@{ ep=$_.Name; n=$_.Count
    empty=($_.Group | Where-Object len -eq 0).Count
    unparsed=($_.Group | Where-Object { -not $_.parsed }).Count }
} | Sort-Object empty -Descending | Format-Table -AutoSize
【反例】把 offsets 数组写成 []（空数组）而不是 null，客户端认为"这次配置有效但没有任何偏移"，于是清空了上一代配置，功能全灭且不报错。教训："空"和"没有"在客户端是两种语义，必须逐一确认。

纪律违反后果
一次只改一条链路出问题无法定位，只能"再来一轮"
先建状态再发增量增量被静默丢弃（客户端没有该实体）
先定"构造源"再谈注入改的是展示层，真实数据没变
每次切片都留正对照无法区分"没生效"与"生效了没用"

9.4 回归矩阵：版本 × 渠道 × 卡类型

维度取值必测组合
CLIENT_VER最新 / 次新 / 最低支持3
CHANNEL默认 / 灰度2
卡类型计时 / 包月 / 永久 / 试用4
网络正常 / 高延迟 / 断线重连3

全测 144 组没必要。必测的是"交叉最危险"的 12 组：最低版本 × 计时卡 × 断线重连、最新版本 × 灰度 × 永久卡……选组合的原则是"任一方变更即可能导致解析失败"。

9.5 本章要点

  1. 偏移表正确性只能靠下游产物判，HTTP 200 不算。
  2. 四种假成功形态各有检出法，空 body 与"空数组"最坑。
  3. 切片纪律四条，缺一条就会进入"再来一轮"循环。
  4. 回归矩阵测交叉最危险的组合，不测全排列。

第 10 章 卡盟与分销对接

10.1 卡盟的三种交互与状态机

交互方向内容幂等键
发卡你的服务端 → CARDMALL_API请求生成 N 张卡（批次、时长、单价）batch_id
查卡卡盟 → 你的服务端（或你主动查）卡是否已售/已激活LICENSE_KEY
回调卡盟 → 你的服务端"某订单已支付，发卡"order_no
[下单] → [支付] → [回调: 发卡] → [用户激活] → [结算]
              ↘ 回调失败 → [重试队列] → [人工补发]

三种交互的顺序不能乱：先发卡后支付 = 白送；先激活后回调 = 用户拿不到卡；回调不幂等 = 重复发卡（一次支付发 10 张，这是最常见的资损形态）。

10.2 卡密生成规则

要素常见做法你要决定的
前缀产品代号（XX-）是否含批次信息
主体16–24 位大写字母数字是否剔除易混字符（0/O、1/I）
校验位1–2 位（Luhn/mod 36/自研）客户端是否校验（校验就必须复刻）
分组4-4-4-4影响用户输入体验与 OCR 容错
唯一性数据库唯一索引 + 生成时查重撞库概率要算（见下）

撞库概率（生日问题近似）：字符集 32、主体长度 16，空间约 32^16 ≈ 1.2e24；发 100 万张时碰撞概率约 n²/2N ≈ 4e-13，可忽略。但如果主体只有 8 位，32^8 = 1.1e12，100 万张碰撞概率约 4.5e-7——仍然小，可一旦撞上就是"两个人同一张卡"，所以唯一索引必须有。

【判据】卡密生成的验收：生成 10 万张 → ① 唯一索引零冲突；② 抽样 1000 张能被客户端格式校验通过；③ 一张已激活的卡不能被再次"生成"出来。

10.3 回调的签名与重放

风险现象处置
无签名任何人 POST 你的回调地址就能发卡必须有签名，sign = HMAC_SHA256(body, SIG_KEY)
签名不含时间重放昨天的回调仍能发卡签名串必须含 REPLAY_TS + order_no
不校验金额1 分钱买年卡回调里的 amount 必须与自己的订单记录比对
回调重试同一 order_no 发多次卡幂等：order_no 唯一索引 + "已处理"短路
# 回调验签的最小实现（顺序即契约，顺序错了永远验不过）
import hmac, hashlib, time
def verify(body: dict, sig: str, key: str, window=300):
    if abs(time.time() - int(body['ts'])) > window: return False
    raw = '&'.join(f'{k}={body[k]}' for k in sorted(body) if k not in ('sign',) and body[k] != '')
    return hmac.compare_digest(hmac.new(key.encode(), raw.encode(), hashlib.sha256).hexdigest(), sig)

项公式常见偏差
应收售价 × 数量用了"面价"而非"代理价"
实收应收 − 手续费手续费率按阶梯，容易算错档
已结算Σ(订单金额)漏了退款单（负数未计入）

10.5 幂等与超时补偿

场景幂等键补偿动作
回调重复order_no直接返回 ok，不重复发卡
发卡超时（卡盟侧超时但你已发）batch_id + seq查卡接口对账，缺的补
用户退款后仍能用order_no + 卡状态退款时把卡置 refunded，下次心跳拒
【判据】幂等的唯一判据：同一请求发 10 次，数据库里只有 1 张卡、1 条订单、1 条审计。跑一次压测脚本就能验。

10.6 本章要点

  1. 三种交互顺序不能乱；回调不幂等是最常见的资损形态。
  2. 卡密要算碰撞概率，唯一索引是底线。
  3. 回调签名必须含时间与订单号，并校验金额。
  4. 对账要查"悬挂单"，差额不为 0 时先查它。
  5. 幂等用"发 10 次只有 1 条"验证，不靠代码走读。

第 11 章 风控识别面：客户端上报了什么，封禁怎么下发

这一章的目的只有一个：让你自建的服务端知道"上游会看什么"，从而在自建侧做等价约束，避免"自建服能用但用户第二天全被封"。

11.1 客户端上报通道清单

通道时机典型字段用途
登录上报首次认证HWID、系统版本、CPU/内存、进程列表、已加载模块、游戏路径设备画像、异常检测
心跳上报每周期在线时长、功能开关状态、宿主窗口标题、内存读写次数行为画像
异常上报崩溃/校验失败堆栈、模块哈希、失败原因码反调试对抗
统计上报启动/退出版本、渠道、卡类型运营数据
静默上报不定时可疑进程名（反外挂/杀软/调试器）最容易被忽略：它可能不在心跳里，而是独立端点

识别方法：把抓包按"端点出现频次"排序，凡是低频但稳定出现的端点，多半是上报类，逐个读字段。判据：字段里出现"进程名/模块名/窗口标题"这类与业务无关的内容，就是上报。

11.2 服务端可观测的"非人类"特征

特征说明自建侧怎么处理
请求间隔过于精确人类有抖动，脚本没有（标准差 <5ms）加抖动容忍，或直接视为机器人
同一 HWID 绑大量卡卡商/工作室限额（如 ≤3）
同一卡 7×24 在线挂机/共享单日在线上限
UA/首部缺失或恒定自研客户端常见，但如果它偶尔变化说明有伪装记录基线
时区与 IP 地理长期不符代理/共享只记录，不阻断
指纹字段全为默认值采集失败被吞视为异常设备
【判据】判断"这是不是真人"永远不要用单一特征；用三条同向特征，任一反向就不下结论（这一条来自第 9 章的负对照思路）。

11.3 封禁名单怎么下发（三种形态）

形态位置生效时机判别
登录时拒绝登录 code立即改 banned=1 看登录响应
名单随配置下发CFG_BLOB 里的 blacklist[]下一次拉配置在 blob 内层找 hwid/key 列表
独立端点查询/auth/check每次启动端点表里的冷门短请求

你的自建侧必须实现"能封、能解、能解释"：封禁要留原因码与时间，解封要能精确恢复；不要用"删卡"代替封禁（删了就恢复不了，且用户会看到"卡不存在"，投诉无门）。

11.4 双端并存时的状态不一致

如果上游还在跑（用户同时能连上游和你的服），会出现：

不一致表现处置
时间账本分叉你的服扣时、上游也扣时 → 用户时间双倍消耗明确"只连一个"，或在配置里指向单一 API_BASE
顶号互踢两个服各自判顶号 → 用户被反复踢只让一个服持有会话
配置代次错乱客户端在两份 cfg_ver 之间来回切让 cfg_ver 单调递增且全局唯一

11.5 本章要点

  1. 上报通道有五种，静默上报最容易漏。
  2. "非人类"判定要三条同向特征，单条不下结论。
  3. 封禁三种下发形态，自建侧必须能封/解/解释。
  4. 双端并存必然分叉，先决定"只连一个"。

B.2 AES-CBC 解密骨架（含 IV 两种位置）

from Crypto.Cipher import AES
from Crypto.Util.Padding import unpad
def dec(key: bytes, blob: bytes):
    for iv_mode in ('prefix','zero'):
        iv = blob[:16] if iv_mode == 'prefix' else b'\x00'*16
        ct = blob[16:] if iv_mode == 'prefix' else blob
        for pad in (True, False):
            try:
                pt = AES.new(key, AES.MODE_CBC, iv).decrypt(ct)
                pt = unpad(pt, 16) if pad else pt
                if pt[:2] in (b'\x1f\x8b', b'x\x9c') or pt[:1] in (b'{', b'['):
                    return iv_mode, pad, pt
            except Exception:
                pass
    raise ValueError('undecodable')

B.3 RC4（自研实现常见，注意它与标准实现可能差一个字节）

def rc4(key: bytes, data: bytes) -> bytes:
    S = list(range(256)); j = 0
    for i in range(256):
        j = (j + S[i] + key[i % len(key)]) & 0xFF
        S[i], S[j] = S[j], S[i]
    i = j = 0; out = bytearray()
    for b in data:
        i = (i + 1) & 0xFF; j = (j + S[i]) & 0xFF
        S[i], S[j] = S[j], S[i]
        out.append(b ^ S[(S[i] + S[j]) & 0xFF])
    return bytes(out)

B.4 签名候选枚举（4.4 的实现）

def candidates(body, key):
    items = [(k, str(v)) for k, v in body.items() if k != 'sign' and str(v) != '']
    for order in (sorted(items), items):
        for sep in ('', '&', '|'):
            for fmt in ('{k}={v}', '{v}'):
                s = sep.join(fmt.format(k=k, v=v) for k, v in order)
                for tail in (key, key.lower()):
                    yield s + tail
