说明 · 这个仓库是什么

本文件是仓库对外的总说明。四份正文文档的定位见 README.md。

一、一句话

把某个外挂套件背后的私有服务端（授权/卡密、配置与偏移表下发、版本更新、心跳与远程指令、卡盟对接）从「只能连、看不懂」，还原成「可自托管、可对账、可运维」的一台服务器，并把过程抽象成换目标可直接套用的方法与判据。

仓库里没有目标的名字、域名、密钥、卡密、内部编号 —— 只有「遇到什么形状的问题、按什么顺序动手、在哪一步最容易翻车、怎么证明自己没骗自己」。

二、内容性质：这是「方法」，不是「复现包」

维度本仓库私有工作区（不公开）
载体可迁移的流程、判据、坑表、验收项具体样本哈希、抓包、真实端点与密钥
可用性换 TARGET 直接套用只对那一个目标有效
生命周期长期有效，随方法论演进随上游改版而失效
去标识强约束：正文不出现身份类字面量不适用

推论：拿它当"照着敲就能通"的脚本会失望；拿它当"该问什么、该验什么、该在哪儿停手"的决策框架，才是正确用法。

四、建议阅读顺序

  1. 本文件 + README.md —— 建立"方法论而非教程"的预期。
  2. 主文档第 0 章「总纲」 —— 三条前提的实证动作（断网 / 黑洞 / 空 200），10 分钟能做完；这一步不做，后面全部白读。
  3. GENERIC_CHECKLIST.md 的 P0–P11 主表 —— 建立全局节奏感。
  4. 带问题回主文档 —— 授权卡住看第 6 章，配置下发卡住看第 7 章，"返回 200 但功能不亮"看第 9 章。
  5. 动手前扫 GENERIC_PITFALLS.md —— 43 条，至少一半是"不知道就白干两天"。
  6. 交付前回到「第 13 章 一页速查」过验收十项。

五、抽象化是怎么做的（可信度依据）

原文里所有身份类信息都被替换成占位常量，概念完整保留、字面量全部消失：

  • 外挂套件名 / 发行方 → TARGET
  • 注入模块 / 驱动 → CHEAT_CORE
  • 卡密 / 设备指纹 → LICENSE_KEY / HWID
  • 授权域名与备用列表 → API_BASE / SERVER_HOST
  • 配置加密体 / 偏移表 → CFG_BLOB / OFFSETS_TABLE
  • 签名密钥 / 会话令牌 → SIG_KEY / SESSION_TOKEN
  • 发卡平台 → CARDMALL_API
  • 本机路径与产物 → RESULT_DIR / CAP_FILE / PCAP_FILE
  • 消息语义 → MSG_LOGIN_OK / MSG_AUTH_FAIL / MSG_CFG_PUSH / MSG_HEARTBEAT_ACK / MSG_FORCE_LOGOUT / MSG_UPDATE_AVAIL（编号须重新枚举）

保留不动的是公共技术名词（HTTP/TLS/JSON/protobuf/AES/RC4/TEA/gzip/zlib、Frida/x64dbg/Ghidra/IDA/Wireshark、VMProtect/Themida、scudo/jemalloc 等）—— 这些不指向任何具体目标，删掉只会降低可迁移性。

编号类信息（消息号、错误码、卡密校验位、偏移字段）一律标注「换目标必须重新枚举」：照抄会失败，这是刻意的。

六、使用边界

  • 本仓库是方法论文档，不含可运行工具、目标地址、凭据、卡密或私有数据。
  • 文档描述的是对自有或获授权目标做逆向还原时的工程流程；用于任何环境前，适用规则由使用者所处环境决定，仓库本身不做担保。
  • 引用请注明来源仓库；转载正文请保留本说明与 README.md 的术语改名表，否则"通用版"会退化成"看起来像教程的残缺笔记"。

七、维护

  • 目录名中的 20261119 为首版冻结日；此后按版本日期迭代。
  • 主文档按章演进，坑表按条累积（新增坑直接追加编号，不复用旧号）。
  • 不接受把具体目标的身份信息（名字、域名、编号、账号、密钥）重新写回正文的改动 —— 那会破坏本仓库唯一的护城河：可公开的去标识性。
  • 上一版（游戏服务端重建）保留在 git 历史中，可用 git show <commit>:<path> 取回。
