一、协议与加密（7 条）

坑 01 · HTTP 200 不等于成功：双层状态码被压成一层

  • 触发条件：客户端 L4 网络层只看 HTTP status，业务层再解析 body 里的 code；服务端按 REST 习惯用 4xx/5xx 表达业务失败（MSG_AUTH_FAIL、token 过期、卡密已绑定），或反过来恒回 200 但 body 为空、code 缺失。
  • 现象：客户端卡在 L3 登录窗转圈，服务端 access log 清一色 200、body 是 {"code":1001} 或 0 字节；抓包能看到客户端读完 body 后立刻断连且不重试，点重试仍是同一循环，服务端侧看不到任何「失败」字样。
  • 怎么提前发现：curl -s -i -X POST "http://SERVER_HOST/ENDPOINT" -H "Content-Type: application/json" -d @login.json | Select-String -Pattern "HTTP/|code|msg"；再在客户端里定位解析函数，看 if (resp.code != 0) 与 if (status != 200) 谁先判——谁先判就以谁为准，另一层只是噪声。
  • 处置：服务端所有业务结果一律 200 + {"code":0|非0,"msg":"MSG_AUTH_FAIL","data":{…}}，把 MSG_LOGIN_OK/MSG_AUTH_FAIL/MSG_CFG_PUSH 这些语义常量直接映射进 code 或 msg；4xx 只留给网关层（限流、签名缺失、路径不存在）。错误码表从客户端字符串表反查，不要自创，新造码在客户端只会落到「未知错误」。

坑 02 · gzip 与 AES 的层次顺序被写反

  • 触发条件：CFG_BLOB 的真实管线是「压缩后加密」还是「加密后压缩」没确认；常见错法是按 encrypt(compress(json)) 还原，而官方实现是 compress(encrypt(json))，或漏掉 CBC 尾块 padding 与 16 字节对齐。
  • 现象：CFG_BLOB 下载回来大小正常（4096 的整数倍），解密后前两字节不是 1F 8B，inflate 报 invalid distance too far back；客户端判定配置损坏后丢弃并回退内置偏移，注入时落到错误地址，游戏进程在对局加载阶段崩。
  • 怎么提前发现：curl -s -o CFG_BLOB.bin -w "%{size_download}\n" "http://SERVER_HOST/cfg?ver=CLIENT_VER"，再 xxd -l 32 CFG_BLOB.bin 看头；两种顺序各试一次：python -c "import gzip;print(gzip.decompress(open('CFG_BLOB.bin','rb').read())[:64])"，能解出 { 的那一版就是真的，解不出先怀疑 padding 而不是密钥。
  • 处置：服务端固定一条 encode_pipeline = compress → encrypt → sign，写进代码注释与协议文档；头部留 1 字节 fmt 标志供分流，对存量客户端保留旧解码分支。发布后不要改顺序——顺序一改，所有在网客户端的配置拉取同时失效，且失败是静默的。判断层次最快的办法是看解密后的首字节：1F 8B 说明压缩在外层，直接可读的 { 说明加密在外层、压缩在里层。

坑 03 · 域名列表 XOR 0x5A 存在资源段，strings 抓不到就以为域名运行时下发

  • 触发条件：客户端把 API_BASE/SERVER_HOST 域名表按字节异或 0x5A 存在 .rdata 或资源节，带长度前缀与可能的二次校验；逆向只跑 strings 没命中，就判断「域名由服务端下发」，于是自建服务端后客户端永远连旧域名。
  • 现象：抓包只看到对旧域名的 DNS 查询与 TLS 握手失败；客户端日志只有「网络异常，请检查网络」；把 API_BASE 换成本地后依然不走本地，因为真正的域名从解密表里读，配置里的域名只是显示用。
  • 怎么提前发现：strings -el CHEAT_CORE.dll | Select-String -Pattern "http|api|\.com" 无结果时，扫一遍解码：python -c "import re;d=open('CHEAT_CORE.dll','rb').read();print([bytes(b^0x5a for b in m) for m in re.findall(rb'[\x20-\x7e]{6,64}',d) if b'http' in bytes(b^0x5a for b in m)][:5])"；更稳的是在 IDA 里搜 xor + 0x5A 的循环，顺着交叉引用找到解密函数与其调用点。
  • 处置：还原完整域名列表、主备顺序、端口与是否带路径前缀，统一归一成 API_BASE/SERVER_HOST 占位；替换时不要只改可见字符串——资源段可能带长度或 CRC 校验，改完必须重算并在干净机器上验证一次登录，否则「改了但没生效」会浪费一整轮排查。

坑 04 · 时间戳窗口与 NONCE 没落库：改系统时间全挂，重放却通过

  • 触发条件：请求头带 REPLAY_TS（秒或毫秒）+ NONCE，服务端校验 |now - ts| <= 300，但 NONCE 只在进程内存里 Set 过一次、重启即失效，或者根本没校验。
  • 现象：测试机时区偏移 8 小时或系统时间不准，所有请求 MSG_AUTH_FAIL，日志只有一行「签名错误」，看不出是时间问题，于是去查密钥；反过来，把抓到的同一个请求原样重放第二次仍然 200，扣时被重复执行、库存被重复扣减。
  • 怎么提前发现：curl 手搓两个字节完全相同的请求（同 REPLAY_TS、同 NONCE）连发两次，看第二次是否被拒；再把本机时间拨快 600 秒跑一次登录，观察是「全部失败」还是「只有时间校验失败」——两者指向完全不同的修法。
  • 处置：服务端统一 UTC 秒，窗口 ±300s 做成配置项（调试期放宽到 ±1800s 但要在日志里标记）；NONCE 落带 TTL 的 KV，键 nonce:{NONCE}:{HWID}、TTL 600s，写入失败即拒绝；解析层先做位宽判断（13 位按毫秒、10 位按秒），避免客户端改格式后静默错位成 1970 年。

坑 05 · 把 SIG_KEY 当加密密钥：客户端只做验签，不负责解密

  • 触发条件：客户端内置 RSA 公钥，只调用 CryptVerifySignature/EVP_DigestVerify；还原时误以为配置是「用这个 key 加密」，于是在自建服务端用公钥加密下发，或把签名块当成密文去解。
  • 现象：配置能下发、客户端也能收，但签名校验失败后静默回退到内置 OFFSETS_TABLE；UI 一切正常，功能却全是旧偏移，注入到错误地址后游戏崩——很容易被误判成「偏移表写错了」，实际是签名管线没走通。
  • 怎么提前发现：strings -el CHEAT_CORE.dll | Select-String -Pattern "PUBLIC KEY|verify|SHA256|RSA"；在导入表里找 bcrypt/crypt32/openssl 的 verify 类函数，确认它是「验」而不是「解」；再定位签名块的偏移（通常在包尾固定 256 字节）与它覆盖的范围（是否含头部）。
  • 处置：拆成两条独立管线——CFG_BLOB 用对称密钥（AES-CBC/GCM）加密，包尾附 RSA-SHA256 签名，覆盖范围写死为「头部 + 密文」；私钥只放服务端 SIGN_SERVICE，客户端只留公钥；换公钥等于换客户端，属于版本级手术，测试期用 patch 掉校验的方式绕过而不是伪造签名；验签失败的分支通常只写一行 debug 日志就 return false，要把这行日志打开才算真正看见问题，否则一直是「下发成功但没生效」。

坑 06 · 自研 TCP 帧长字段语义不明，按定长读必然错位

  • 触发条件：L4 除 HTTP(S) 外还有一条自研 TCP：2 字节长度 + 1 字节压缩标志 + 1 字节 cmd，长度是「含头」还是「不含头」、大端还是小端未标注；还有一条独立连接只跑心跳。
  • 现象：第一帧解析正常，第二帧开始错位，客户端表现「登录成功但拉配置超时」；服务端日志显示收到了完整字节流却回不出合法帧；解析异常被 catch 吞掉，UI 只显示「初始化失败」，没有任何字段级线索。
  • 怎么提前发现：tshark -r PCAP_FILE -T fields -e tcp.payload | Select-Object -First 5 导出前几帧十六进制，手工按 2 字节切；或写二十行脚本对所有候选口径（含头/不含头 × 大端/小端）各切一遍，能干净切到流尾、且每帧 cmd 都落在已知枚举里的那组才是真的。
  • 处置：先只做「切帧 + 打印 cmd/len」的 dumper，跑通全量 PCAP_FILE 再谈业务；压缩标志对应 zlib raw deflate（无 1F 8B 头），不要用 gzip 解；把长度语义、字节序、压缩算法写进协议表，并给 dumper 加单元测试，防止后续改代码时回归。心跳小包常被单独走一条短连接，切帧脚本必须把两条连接分开看，混读会把控制帧当数据帧解析，错位来源又多一处。

坑 07 · 证书 pinning 让自签证书被静默拒绝

  • 触发条件：客户端对 API_BASE 做证书 pin（整证书哈希或 SPKI 哈希），自建服务端用自签证书 + hosts 指向本地，握手阶段直接被拒；部分实现还把失败重试包在 catch 里，不弹任何提示。
  • 现象：L3 登录窗一直转圈，Fiddler/mitmproxy 里一条请求都看不到（出流量在 TLS 层被掐断）；客户端日志只有「网络异常」；服务端侧零 TLS 握手记录，于是很容易误判成「客户端连的还是旧域名」。
  • 怎么提前发现：先 openssl s_client -connect SERVER_HOST:443 -servername SERVER_HOST -showcerts 看链路是否完整；同时挂 mitmproxy，若完全没有 ClientHello 到代理，说明 pin 生效或在更早的层被拦；再在二进制里搜 32 字节十六进制常量（SHA-256 pin 值）与其交叉引用。
  • 处置：调试期在隔离测试机上 patch 掉校验回调（hook TrustManager/X509Chain 的验证返回值为 true），把「能抓到明文」作为前置里程碑；不要试图伪造 pin——没有对应私钥时唯一可行路径是改客户端，且该改动必须限定在测试环境，交付文档里明确标注「已改客户端」以免后续误判。

二、授权与时间账本（6 条）

坑 08 · token 无状态，于是顶号与强制下线全部失效

  • 触发条件：服务端签发自验 JWT（SESSION_TOKEN 只含 HWID/exp/sig），不维护会话表；而客户端的顶号逻辑与 MSG_FORCE_LOGOUT 依赖服务端主动踢人。
  • 现象：对 A 发 MSG_FORCE_LOGOUT 之后，A 重新用旧 token 拉配置仍然 200，两台机器互踢形成循环；服务端「在线用户」列表与实际连接数长期不一致，运营按在线数投放的活动预算全偏。
  • 怎么提前发现：同一 LICENSE_KEY 在两台不同 HWID 上登录拿两个 token；对 A 发强制下线，立刻用 A 的旧 token 请求 /cfg，看是否仍 200；再观察 A 是否在 5 秒内重新登录成功——三点全中即为无状态 token 的典型症状。
  • 处置：token 里带 sid，服务端维护 sid → (HWID, last_ts, revoked) 表，每次请求校验 sid 未吊销；顶号时把旧 sid 写进 deny 列表，TTL 取 token 剩余有效期（省一次清理任务）；「最近登录者胜」再加 30s 冷却锁，避免互踢风暴把登录 QPS 打满。会话表要有落盘副本，进程重启后顶号状态不能凭空恢复成「两台都在线」，否则一次发版就能让所有顶号白做。

坑 09 · 扣时发生在心跳而不是登录：自建侧在登录扣时导致重复计费

  • 触发条件：官方语义是「登录只验证、心跳按墙钟差扣秒」，还原时把扣时写进登录成功分支，或按固定 interval 扣而不看实际间隔；多开场景下同一账号被扣多次。
  • 现象：用户每次重登都少几分钟，一天重登十次就少半小时；客户端显示剩余时间与服务端账本差出几十分钟，客诉「卡怎么越用越少」；自测时因为只登一次，永远发现不了。
  • 怎么提前发现：单账号登录后不发心跳等 10 分钟，看剩余时间是否变化（正确实现应完全不变）；再连发 10 次心跳看扣减是否线性；最后把心跳间隔人为拉长到 120s，看服务端扣 120 还是扣固定的 30。
  • 处置：扣时唯一入口放在 MSG_HEARTBEAT_ACK 路径，用 min(now - last_heartbeat_ts, MAX_GAP) 扣，MAX_GAP 取 2×正常间隔，防止补发心跳回溯扣时；登录只更新 last_login_ts；扣时流水单独一张表（sid/delta/before/after/ts），对账时求和比对，差额 > 1 秒即视为 bug。

坑 10 · 下发「剩余秒数」而不是「到期时间」：客户端倒计时可回滚

  • 触发条件：登录响应给的是 remain_seconds，客户端 L3 用本地时钟做单调倒计时；退出重进后向服务端重新取一次；服务端只在登录时计算，心跳不回传时间。
  • 现象：客户端显示「剩余 3 天」，断网重进又变回 3 天 2 小时（上次没扣够）；改本机时间 +1 天，在离线缓存窗口内可以白嫖；服务端账本与客户端显示长期分叉，截图无法自证。
  • 怎么提前发现：抓两次登录响应，比对 remain_seconds 与 expire_at 是否同时存在；改本机时间 +1 天后重启客户端，看显示是否被拉回；连续 10 次心跳后对比客户端显示与服务端账本差值，超过 60 秒即说明没有纠偏机制。
  • 处置：两个字段都下发，客户端以 remain_seconds 为准、服务端每次心跳回传 server_ts + remain_seconds 纠正漂移；所有账本运算只用服务端时钟，客户端时间仅用于展示；客户端上报的时间只做异常检测（偏差 > 1 天打标记），不参与任何扣减。

坑 11 · HWID 是多源拼接加盐：换网卡就换绑，克隆机就撞车

  • 触发条件：HWID = hash(主板序列号 + 系统盘序列号 + MAC + 盐)，任一分量变化即视为新设备；盐可能硬编码在客户端，也可能由服务端在首次绑定时下发。
  • 现象：用户换网卡或重装系统后，老 LICENSE_KEY 提示「已绑定其他设备」，客诉量在系统更新季集中爆发；测试机用同一镜像克隆出多台，HWID 完全相同，触发风控或互相顶号，问题在单机上永远复现不了。虚拟机批量部署时更明显：同一镜像的 HWID 完全一致，绑定表上会出现「一台设备绑了十张卡」的异常记录。
  • 怎么提前发现：在客户端搜 GetVolumeInformation/Win32_BaseBoard/GetAdaptersInfo 的调用点，dump 出参与拼接的原始串与盐；两台机器跑同一 build，把算出的 HWID 并排比对，逐分量替换（改 MAC、换盘符）找出哪一项在变。
  • 处置：服务端把 HWID 当不透明字节串（不假设大小写、长度、编码、是否十六进制），只做等值比较与哈希索引；绑定关系留「一次人工换绑」入口并写审计（谁批的、原值、新值）；日志只存 HWID 前 8 位 + 短哈希，避免明文扩散。

坑 12 · 客户端本地授权缓存：服务端全关它还能进游戏

  • 触发条件：客户端把 token/到期时间写注册表或 %APPDATA% 加密文件，离线放行 N 分钟（常见 30–120 分钟）；缓存里有签名字段，TTL 与在线校验是两套逻辑。
  • 现象：服务端停掉后客户端仍能进 L2 跑一段，误判「服务端没起作用」；或者服务端把到期时间改早，客户端因缓存不刷新仍显示未到期，于是判定「改动没下发」；断网启动的窗口长度与文档描述不一致。
  • 怎么提前发现：Procmon 过滤客户端进程的 WriteFile/RegSetValue，找到落盘位置与写入频率；断网启动一次，记录从启动到被拦的分钟数；再对比缓存文件 mtime 与最近一次登录时间，确认缓存是否被复用。
  • 处置：自建服务端必须复刻缓存格式与 TTL，否则「看起来全通了，一断网就废」；缓存里通常有签名字段，改任何字段都要按客户端算法重签，照抄比自创省事；文档里把「离线窗口」写成明确数字，测试用例覆盖「窗口内」与「窗口外」两态。

坑 13 · 错误判定有优先级，客户端只认第一个命中的码

  • 触发条件：服务端同时返回 banned、expired、conflict 多个标志，客户端按「封禁 > 到期 > 顶号 > 正常」取第一个；错误码映射表是客户端内置的，未收录的码统一显示「未知错误」。
  • 现象：一个既封禁又到期的 LICENSE_KEY 在客户端显示「已到期」，排查方向直接跑偏到时间账本；服务端返回了 MSG_AUTH_FAIL 但客户端文案是「网络异常」，因为 code 值不在映射表里；同一份响应在两端解读出完全不同的原因。
  • 怎么提前发现：构造同时满足两个条件的测试卡（封禁 + 过期），看客户端文案命中哪一个；再把响应体字段逐个删掉做二分，确认客户端到底读哪个键；最后把 code 改成映射表里没有的值，看回落行为。
  • 处置：服务端按客户端优先级只返回一个主错误码，其余放 detail 供日志与工单；错误码与 MSG_* 常量必须从客户端字符串表反查对齐，未知码一律回落「通用失败」而不是新造码；两端共用一份错误码表，改动走同一份清单。

三、配置与更新（6 条）

坑 14 · CFG_BLOB 里 offsets 与 feature code 必须同代，跨代拼装必崩

  • 触发条件：CFG_BLOB 同时携带 OFFSETS_TABLE 与功能开关/feature code，两者由同一 CLIENT_VER + 游戏版本生成；还原时把新 offsets 配旧 feature code（或反过来）混着下发，以为字段独立。
  • 现象：客户端注入到错误地址，游戏在进入对局后崩溃；服务端日志一切正常（200、CRC 也对、大小也对），因为破坏发生在客户端内存层，网络层看不到任何异常；换回旧配置立刻恢复，很容易被误判成「游戏更新了」。
  • 怎么提前发现：dump CFG_BLOB 头部，通常有 cfg_ver/game_ver/build 三个字段，与客户端上报的 CLIENT_VER 逐一比对；发布前用已知样本做一次「注入后能否通过客户端自身 CRC 复核 + 功能开关是否命中预期分支」的断言。
  • 处置：配置按 (game_ver, CLIENT_VER, CHANNEL) 三元组做键，禁止跨代混装；服务端保留最近 3–5 代并做启动自检（用历史样本回放，确认每代 offsets 都能通过客户端校验）；三元组缺失时拒绝下发而不是回落到默认值——回落的默认值往往正好是「能跑但跑错」的那一代。上线前对每代配置跑一次「注入 + 读内存校验」的端到端，光看下发成功不算数。

坑 15 · 偏移表下发后客户端会用自身 CRC 复核，改值不改 CRC 等于没发

  • 触发条件：OFFSETS_TABLE 尾部 4 字节是客户端计算的 CRC32，客户端拉到后自己算一遍再比对，不一致直接丢弃并回退内置表；CRC 覆盖范围可能是「不含头」或「含头不含尾」，两者差 8 字节。
  • 现象：服务端改了某个 offset 值，客户端功能毫无变化且无任何报错；只有把客户端日志级别调到 debug 才能看到一行 cfg crc mismatch, fallback；于是怀疑下发失败、怀疑缓存，浪费一整天。
  • 怎么提前发现：python -c "import zlib;d=open('offsets.bin','rb').read();print(hex(zlib.crc32(d[:-4])&0xffffffff), d[-4:].hex())"，两个值不等就说明 CRC 没跟着更新；在客户端搜 0xEDB88320 常量确认算法与覆盖范围，别假设是标准 CRC32。
  • 处置：所有下发包统一走 build_cfg() 计算并写入 CRC，禁止手改二进制；把「CRC 自检」做成发布门禁，CI 里对每个产物跑一遍客户端同款算法；CRC 校验失败时服务端侧也要能感知（客户端回报 cfg_bad_crc 事件），否则永远只能靠人眼发现。

坑 16 · 强制更新写 force=1 没用，客户端只认 ver_new

  • 触发条件：更新检查响应里 force 与 ver_new 是两个字段，客户端逻辑是「读 ver_new 与本地版本比较，有差异才提示，force 只决定能否跳过」；版本的编码格式（"1.2.3"、四段整数、hex）由客户端解析函数决定。
  • 现象：只置 force=1 不填 ver_new，客户端认为无更新，永远停在旧版；填了 ver_new 但格式不匹配导致比较异常，同样不更新；更隐蔽的是更新了但 url 为空，客户端弹窗后点「更新」无反应，用户以为网络问题。
  • 怎么提前发现：抓一次更新检查响应，把 ver_new 改成明显更大的值看客户端是否弹窗；再单独改 force（ver_new 不动）看是否只影响「能否跳过」；两次实验就能确定字段权重，不必读完全部反汇编。
  • 处置：字段格式从客户端解析函数反查，服务端把 force/ver_new/url/hash/size 全部填对，多填不影响；ver_new 用客户端同款编码，别改成人类可读串；灰度发布时先只对测试 CHANNEL 置 force=1，验证「不能跳过」的行为再全量。

坑 17 · 更新包走 302 到 CDN，直连源站被判异常

  • 触发条件：更新 URL 是短链，客户端跟随 302 到 CDN 拉取；自建时把文件直接放源站、改了 Host，或没实现 Range 断点续传；清单里的哈希与文件不是同批产出。
  • 现象：本机 curl -L 能下完，客户端下载进度停在 0%；或下完校验失败进入「删除重下」无限循环；服务端日志只有一条 302，看不到后续请求，于是误判客户端没发请求。实际上客户端已经把请求打到 CDN，源站日志里当然没有；只看源站日志，会把「分发成功」误读成「客户端没动作」。
  • 怎么提前发现：curl -sIL "http://SERVER_HOST/upd/latest" | Select-String -Pattern "HTTP/|Location|ETag|Content-Length|Accept-Ranges" 看跳转链与头；抓包看客户端是否带 Range/If-None-Match（带 Range 说明必须支持 206，否则只能整包重下）。
  • 处置：保留 302 结构，补齐 ETag/Content-Length/Accept-Ranges；文件哈希（md5/sha256）与清单同批产出，发布脚本先算后写；测试矩阵加一项「限速 200KB/s + 中断续传」，这条最容易被忽略也最容易在弱网用户身上爆。

坑 18 · 配置下发是增量 patch，缺 baseline 的新客户端全崩

  • 触发条件：服务端只下发 diff（变更键），客户端本地有 cfg_rev 基线并自行合并；基线版本可能被清理、被缓存覆盖或被用户手动删目录。
  • 现象：自建服务端只发 diff，老用户正常、全新安装的用户拿不到基线，合并后配置缺字段，客户端在 L2 初始化时崩或功能缺失；清空配置目录可 100% 复现，但在「一直在用的测试机」上永远看不到。
  • 怎么提前发现：清空客户端配置目录后再登录，看是否还能拿到完整配置；对比「首次登录」与「第二次登录」的响应体长度（首次应明显更大，差一个数量级才对）；在请求体里找 cfg_rev 字段，确认客户端确实会上报基线版本。
  • 处置：服务端维护 per-HWID 的 cfg_rev，跌破已知基线一律发全量；diff 合并放服务端算（服务端持全量状态），客户端只保留「全量覆盖」这一条路径最稳；cfg_rev 单调递增且与 CFG_BLOB 头部版本一致。

坑 19 · CLIENT_VER / CHANNEL 决定配置分支，缺 channel 落默认分支

  • 触发条件：配置按 CLIENT_VER + CHANNEL（正式/测试/代理）分支，请求缺 channel 时服务端回落默认分支；渠道表与 CARDMALL_API 的渠道 ID 是两套编号。
  • 现象：代理渠道客户端拿到正式渠道配置，价格、功能开关、API_BASE 全不对；服务端日志里 channel 为空却没有任何告警；问题只在特定渠道用户身上出现，内部测试全绿。
  • 怎么提前发现：登录请求体里找 channel 字段并在服务端日志打印；用两个不同 channel 值请求同一接口，用 Compare-Object 对响应做 diff，差异为空说明分支没生效；再看渠道表与卡盟渠道 ID 是否能一一映射。
  • 处置：channel 缺失时按「最保守分支」处理（只发基础功能，不发实验特性），并在响应里回显 channel 便于核对；渠道表与卡盟渠道 ID 建显式映射表，缺映射时拒绝发货而不是猜；新渠道上线前固定跑一次「渠道 × 版本」矩阵。

四、心跳与指令（5 条）

坑 20 · 心跳失败会指数退避，服务端按固定 30s 判离线必然误判

  • 触发条件：客户端心跳失败后间隔翻倍（30→60→120→240s），服务端用「last_seen 超过 30s 即离线」判定；统计口径把「单次心跳缺失」当成下线事件。
  • 现象：网络抖动一次后客户端显示离线，其实还在退避重连；服务端在线数忽高忽低，报表与卡盟后台对不上；运营按在线数做的活动预算与库存全偏，且每次抖动幅度不同，无法对账。
  • 怎么提前发现：断网 60s 再恢复，抓包量心跳间隔序列（应看到 2/4/8/16s 的退避阶梯）；把服务端离线阈值临时改成 300s，看在线上报是否稳定；统计「离线事件数 / 实际断线数」的比值，远大于 1 即判定口径错。
  • 处置：在线判定用 last_seen 的宽松阈值（≥3×最大退避间隔），下线事件延迟触发；MSG_HEARTBEAT_ACK 带 server_ts 让客户端校正；把「离线」定义为「超过阈值无心跳且无重连尝试」，并在报表里单列「退避中」状态。客户端的退避参数要从抓包实测拿，别抄默认值——不同版本的初始间隔与上限差别很大，抄错会让阈值一直偏。

坑 21 · 远程指令没有 seq 与幂等，重发就重复执行

  • 触发条件：指令帧带 cmd_id/seq，客户端记录已执行的最大 seq 并丢弃重复包；服务端未持久化发送状态，靠「没收到 ACK 就重发」驱动，重发窗口与网络抖动叠加。
  • 现象：重复下发「清理缓存」只是多跑一次，但重复下发「重启 loader」就把客户端变砖；重复下发「下发配置」导致客户端连续重载两次、UI 闪断；危险指令一旦重复，用户侧表现为「用了两天突然坏了」。
  • 怎么提前发现：对同一 cmd_id 连发两次，观察客户端行为是否叠加（看日志里的执行计数）；抓包确认客户端是否回 cmd_ack，ACK 里带的是 cmd_id 还是 seq；再把 ACK 丢掉看服务端重发几次、间隔如何。
  • 处置：服务端指令表持久化 (cmd_id, seq, state, sent_at, ack_at)，只在无 ACK 时按退避重发且 seq 严格递增；客户端侧也做幂等（服务端不可信时的双保险）；危险指令（重启/卸载/清配置）加二次确认与 5 分钟冷却，并把执行结果回传成结构化事件。

坑 22 · MSG_FORCE_LOGOUT 只清 UI，客户端照样重连

  • 触发条件：客户端收到 MSG_FORCE_LOGOUT 只弹窗 + 清本地 UI 状态，重连定时器仍在跑，旧 token 仍被服务端接受；服务端吊销逻辑只删了会话缓存没写 deny 列表。
  • 现象：顶号后两台机器互相踢，形成「踢来踢去」的循环；用户侧反复弹「账号在其他设备登录」；服务端登录 QPS 异常升高，连接数抖动，日志里同一 HWID 一分钟内出现十几次登录。
  • 怎么提前发现：A 登录 → B 登录 → 观察 A 是否在 5 秒内重新登录成功；统计同一 HWID 一分钟内的登录次数，超过 3 次即为踢人循环；再看 MSG_FORCE_LOGOUT 的响应里是否带原因码（没有的话客户端无法区分「被踢」与「网络断了」）。
  • 处置：顶号时服务端同时吊销旧 sid 并按 HWID 做「最近登录者胜」；加 Redis 锁 + 30s 冷却，同一 HWID 冷却期内只允许一次切换；MSG_FORCE_LOGOUT 带原因码，客户端据此决定「停止重连」还是「退避重试」，这是打断循环的唯一开关。

坑 23 · 指令通道复用业务长连接，长轮询把连接占满

  • 触发条件：远程指令走长轮询或同一条 WSS，业务请求（拉配置、上报统计）与指令共用连接池；长轮询超时设成 60s 且大于中间设备 NAT 超时；服务端连接上限按「用户数」而不是「连接数」估算。
  • 现象：指令延迟从秒级涨到数分钟，客户端表现为「点了没反应」；服务端连接数打满，新登录请求排队超时；重启服务端后短时间恢复又复发，像是周期性故障。
  • 怎么提前发现：看连接数曲线（(Get-NetTCPConnection -State Established).Count）与「指令下发 → ACK」的 p95 时延；把长轮询超时改成 25s 观察延迟是否下降；统计每条连接承载的业务请求数，远大于 1 即说明复用过度。
  • 处置：指令走独立 topic 或独立短连接；长轮询超时 25s（小于常见 30s NAT 超时），超时返回空包维持；连接池按用途隔离，业务与指令不共享配额，并给指令通道单独做延迟告警（p95 > 5s 即报）。

坑 24 · 心跳 ACK 不带服务端时间，客户端倒计时与服务端账本越走越远

  • 触发条件：MSG_HEARTBEAT_ACK 只回 {"code":0}，客户端纯本地计时；服务端按自己时钟扣时；客户端时钟漂移（虚拟机休眠、主板电池、手动改时间）没有任何纠正通道。
  • 现象：客户端显示「还有 3 天」，服务端账本已到期直接 MSG_AUTH_FAIL；用户截图与后台数据对不上，客诉无法自证；虚拟机挂起恢复后时间跳变，客户端瞬间显示「已到期」。
  • 怎么提前发现：抓 ACK 看是否有时间字段；把本机时间改 ±1 小时后看客户端剩余时间是否被拉回；连续 10 次心跳后对比客户端显示与服务端账本的差值，超过一个心跳间隔即说明缺少纠偏。
  • 处置：ACK 必带 server_ts 与 remain_seconds，客户端用差值修正本地倒计时；服务端账本永远用自己时钟，客户端上报时间只做异常检测；虚拟机场景额外用单调时钟（QueryPerformanceCounter）计时，避免挂起恢复后的时间跳变。

五、卡盟与分销（5 条）

坑 25 · 卡盟回调没有签名，抓到自己一次回调就能重放发货

  • 触发条件：CARDMALL_API 的发卡回调只带 order_id/LICENSE_KEY/数量，没有签名、时间戳或来源校验；服务端处理逻辑是「收到即发货」，靠上游守规矩。
  • 现象：把抓到的一次回调原样 curl 重发，服务端仍然 200 并再发一张卡/再加时长；对账时库存对不上，代理侧多出货；问题往往在跑了一次压测或重试脚本之后才被发现，此时已经多发了若干张。
  • 怎么提前发现：用同一 body 连发两次，看第二次是否仍 200 且产生副作用（查订单表行数与卡密表新增）；检查回调处理里是否校验 REPLAY_TS/NONCE 或来源 IP；再看 order_id 上有没有唯一索引。
  • 处置：自建侧做补偿控制——order_id 当幂等键 + 状态机只允许 pending → paid 一次；回调来源加 IP 白名单（CARDMALL_IP 占位）与共享密钥 HMAC；原协议没签名时至少落去重表（order_id 唯一索引），重复回调返回 200 但不动数据，日志记 duplicate_callback 事件。

坑 26 · 卡密状态机缺状态：退单的卡还能登，一张卡发两次

  • 触发条件：状态只有 未使用 / 已使用，没有 已绑定 / 已冻结 / 已退单 / 已换绑；绑定关系存在卡密行上而不是独立表；退单走物理删除。
  • 现象：退单的 LICENSE_KEY 仍能登录；同一张卡被两个订单发货（并发回调或重试）；用户换绑后旧绑定关系仍在，两台设备都能用；查库存时数字对不上但找不到是哪张卡错了。
  • 怎么提前发现：对同一 LICENSE_KEY 走完整链路「发卡 → 绑定 → 退单 → 登录」，看登录是否被拒；再并发发两个同卡订单，看库存是否变负；查表里 status 的实际取值集合与代码分支是否一一对应，多出来的值就是隐患。
  • 处置：显式状态机 + 变更流水表（谁、何时、从什么状态到什么状态、依据哪个工单）；登录只认 active 且未过期；退单走「冻结」而不是物理删除，保留可追溯；绑定关系放独立表，按 (LICENSE_KEY, HWID) 唯一索引。状态变更必须走同一个入口函数，任何「直接 UPDATE status」的旁路，都会在三个月后变成对不上的账。

坑 27 · 查询接口与回调双通道，主备数据长期不一致

  • 触发条件：卡盟侧有「订单查询」和「发货回调」两条通道，回调可能丢包，查询是拉模式；两条通道的订单号不同源（一边内部 ID、一边卡盟 ID），对账时靠人工映射。
  • 现象：回调丢了但查询有记录 → 用户付了钱没到账；或者回调到了两次、查询只一条 → 重复发货；对账日报与实际库存差几张，且差值每天漂移，越查越乱。
  • 怎么提前发现：对比同一 order_id 在两条通道的 status 与时间戳（REPLAY_TS 量级差）；按小时统计回调缺失率；写一个只读对账脚本扫「5 分钟前仍 pending」的订单并主动查询，把差异写文件。
  • 处置：以回调为准、查询做补偿（定时任务扫 pending 主动查，查到即补发且幂等）；对账脚本每天跑一次，差异落 RESULT_DIR/recon_YYYYMMDD.csv；两条通道的 order_id 必须同源，映射表放服务端维护并在启动时校验完整性。

坑 28 · 金额单位混用：分 / 元 / 浮点，差一分能查一整天

  • 触发条件：CARDMALL_API 里 price 有的是「分」的整数（100 表示 1 元），有的是浮点元（1.00）；代理分成按百分比，结算时四舍五入方向不一致；优惠券与退款各算一次又叠加。
  • 现象：0.01 元的测试单变成 1 元；分成算出 0.30000000000000004 这类浮点尾巴，月度对账差几分钱，代理拒绝对账；退款金额与原单差 1 分，用户投诉「少退一分」。
  • 怎么提前发现：抓一笔 0.01 元测试单跑全链路，看每个环节落库的量级；检查响应里 price/amount/fee 字段的取值范围（整数 100 vs 1.00）；用整数运算重算一遍分成，与系统结果逐笔比对。
  • 处置：内部一律整数「分」，入口做单位识别（> 10000 视为分，否则视为元并 ×100），出口按展示需要转元；分成用整数乘除 + 明确舍入方向（向下取整给平台、余额留代理），并在流水里记录舍入差额，让对账能解释每一分。所有金额字段在接口文档里标注单位，别只靠字段名猜——amount 与 amount_fen 同时存在时，先看哪个被客户端真正使用。

坑 29 · 卡密批量导入的编码与换行：带 BOM 的前几条注定登录失败

  • 触发条件：代理给的 CSV 是 UTF-8 with BOM + CRLF，混有全角字符、首尾空格、重复行；导入器按无 BOM 读取，或按 \n 切行；去重只比字符串不做规范化。
  • 现象：导入后前几条卡密的 LICENSE_KEY 带 \uFEFF 或 \r，用户复制粘贴登录一律 MSG_AUTH_FAIL；重复导入产生重复卡，库存虚高；同一张卡在库里有两条记录，绑定关系分裂。
  • 怎么提前发现：Get-Content cards.csv -Encoding Byte -TotalCount 3 看是否 EF BB BF；(Get-Content cards.csv).Count 与入库行数比对；对入库数据跑 SELECT COUNT(*) - COUNT(DISTINCT key)，不等于 0 即存在重复或不可见字符。
  • 处置：导入器统一 UTF-8 无 BOM 读取 + Trim() + 全角转半角 + 按 LICENSE_KEY 哈希去重；失败行输出 RESULT_DIR/import_err.csv（行号 + 原因）；导入前先 dry-run 出报告再落库，把「行数一致 + 零重复」做成硬门禁。

六、客户端副产物（5 条）

坑 30 · 客户端日志与崩溃 dump 里已经写好了协议，却在忙着逆二进制

  • 触发条件：TARGET 客户端 debug 版本或崩溃报告里带完整 URL、请求 JSON 模板、错误码与字段名；dump 里保存了网络函数的调用栈与参数；逆向时跳过这一步直接上 IDA。
  • 现象：花几天逆 TLS 与序列化，其实日志里早有 API_BASE、请求体样例与字段语义；dump 里能看到网络函数的调用栈与实参，能直接把协议还原到字段级；最终两套结论还不一致，需要再花时间调和。
  • 怎么提前发现：Get-ChildItem -Recurse "$env:LOCALAPPDATA\TARGET","$env:APPDATA\TARGET" -Include .log,.txt,*.dmp -ErrorAction SilentlyContinue | Select-String -Pattern "http|token|code|cfg" | Select-Object -First 40；有 .dmp 就用 WinDbg 加载，!analyze -v 找异常模块，k 看崩溃线程栈。
  • 处置：把日志当第一手协议文档，字段名与枚举值直接照抄（不要改名，改名会让后续对照成本翻倍）；dump 里定位网络函数后回到 IDA/x64dbg 交叉验证，形成「日志给字段、反汇编给语义」的双证据链；这套顺序能省掉一半以上的逆向工时。

坑 31 · 本地配置缓存只做了单字节异或，自建服务端却把加密做太重

  • 触发条件：CFG_BLOB 网络传输是 AES，但客户端落盘缓存只做 XOR/Base64；还原时按网络层格式设计本地缓存；缓存头带版本号与 CRC，格式与网络包并不相同。
  • 现象：自建服务端下发的配置客户端能解，但落盘后重进客户端读不出来，反复回源拉配置；缓存被判定损坏后清空，离线能力丢失；每次启动都多一次全量请求，流量与延迟都翻倍。
  • 怎么提前发现：Procmon 找写文件路径，xxd -l 64 cache.bin 看头；对缓存做 256 次单字节 XOR 爆破，找出能打印的那一版；对比缓存头 8 字节与网络包头的差异，确认两者不是同一套结构。
  • 处置：缓存格式照抄（含头部版本号、长度、CRC），这样离线启动与增量 patch 才能对齐；网络层与本地层用两套独立编解码函数，别图省事复用；缓存目录位置与文件名也照抄，否则客户端找不到会当首次启动处理。

坑 32 · loader 的哈希校验在「已是最新」分支被跳过

  • 触发条件：更新清单带 sha256，但 loader 逻辑是「版本号相同 → 直接用本地文件」，只有真正下载时才校验；本地版本号缓存在注册表里，可以手改。
  • 现象：本地改过的包能跑，换到干净机器上被拒；或反过来，干净机器被投毒包利用；测试结论在两种环境互相矛盾，白排查一整天，最后发现差异只在「是否已存在同版本文件」。
  • 怎么提前发现：把本地文件改一个字节再启动，看是否触发重下（不重下说明走了跳过分支）；同一份包分别在「目录为空」与「已是同版本」两种状态下各启动一次，比对行为与日志。
  • 处置：自建分发时哈希必须真实计算，且清单与文件同批产出；测试矩阵固定包含「干净机器首次安装」与「同版本覆盖安装」两项，缺一项就不算验证过；发布脚本里对每个包跑两次安装（空目录 + 覆盖），任一失败即阻断发布。手动改本地文件验证跳过分支时，记得改完还原，否则下一次测试的基线就是脏的，结论直接反过来。

坑 33 · 域名有多个 + 失败熔断，只起一个服务就永远连不上

  • 触发条件：客户端内置域名列表（3–5 个主备），失败计数到阈值后熔断并进入冷却（常见 5 分钟）；列表顺序可能参与某种校验，不能随意删改。
  • 现象：只在列表第一个域名上起了服务，第一次失败后客户端 5 分钟内不再尝试，表现为「彻底连不上」；重启客户端才恢复，很容易被误判成服务端崩了；换台机器又能连，因为熔断状态是本地存的。
  • 怎么提前发现：抓 DNS 查询序列，看客户端到底解析了哪几个域名、间隔多久；数「失败几次后切换」，再改 hosts 让目标全失败，记录下一次尝试的时间差即为冷却时长；检查熔断计数是否落盘（落盘意味着重启也不会清零）。
  • 处置：自建时同时接管列表里所有域名（hosts 或本地 DNS 通配），或按客户端熔断参数把冷却调小；保留原列表顺序，别删域名——顺序本身可能参与哈希校验；测试期把熔断计数文件删掉再启动，避免被历史状态误导。

坑 34 · 驱动加载失败走降级路径，压根不联网，却去查服务端

  • 触发条件：CHEAT_CORE 驱动/内核模块加载失败（测试机没关驱动签名强制、缺运行库、VM 环境被识别），客户端进入纯用户态降级路径，部分版本直接不发起网络请求。
  • 现象：登录窗之前就退到「初始化失败」，服务端侧零请求；或者能进 UI 但所有功能灰掉，看起来像授权失败；在 VM 里测什么都不对，换物理机立刻正常。
  • 怎么提前发现：sc query CHEAT_DRV 看服务状态；fltmc 看过滤驱动是否挂在卷上；客户端日志里找驱动加载返回值（常见 0x80070005/0x8007045B）；对比「有驱动 / 无驱动」两次启动的网络行为差异。
  • 处置：测试矩阵固定两台机器（一台有驱动、一台无驱动），先确认「网络层是否被调用」再排查服务端；VM 里测不出的问题不要归因到协议；客户端初始化顺序若固定为「驱动 → 网络」，则驱动失败必须先修，否则后面所有实验都是无效样本。

七、工程与环境（5 条）

坑 35 · 时区与「按天到期」：UTC 与本地时间混用，跨日结算全错

  • 触发条件：服务端存 UTC，客户端显示本地时间，卡密「按天到期」用本地 00:00 计算；日志一边打 UTC 一边打本地；结算任务按 UTC 时刻触发却按本地日切分。
  • 现象：UTC+8 早上 8 点前到期的卡显示「还没到期」；跨日结算任务在 UTC 16:00 跑，实际是本地次日 00:00，扣时归属错一天；排障时日志时间对不上，把两次请求的顺序看反，得出完全错误的因果。
  • 怎么提前发现：日志统一打 ISO8601 带 Z 与偏移，用 Get-Date -AsUTC 对照；构造一张「今天 23:59 到期」的测试卡，看跨日后剩余时间如何变化；把结算任务的触发时刻与业务日切时刻并排检查。
  • 处置：库内存 UTC 秒；「按天到期」固定一个基准时区（如 UTC+8 的 00:00）并写进文档；展示层转本地；结算任务用固定 UTC 时刻触发并在日志里同时打印两种时间；所有跨日逻辑加一条「基准时区」配置项，禁止散落在代码里。跨日结算要能在测试环境手动触发，否则每次只能等第二天验证，问题平均要多压一天才暴露。

坑 36 · NAT 超时掐断长连接，服务端看不到断开

  • 触发条件：中间设备 30–60s 无流量就回收会话；心跳间隔设成 60s 或更长；长轮询超时超过 NAT 时间；TCP keepalive 默认 2 小时没改。
  • 现象：客户端挂着不动 2 分钟后第一次操作超时，随后重连恢复正常；服务端 last_seen 还停在断开前，连接表里留着「僵尸连接」占用配额；连接数只增不减，最后 accept 失败。
  • 怎么提前发现：空闲 5 分钟后操作一次，抓包看是否有 RST 还是直接超时无响应；量心跳间隔与 NAT 超时的关系（间隔必须明显小于超时）；服务端侧对比 TCP 连接状态与业务会话表，两表条目数不一致即为僵尸连接。
  • 处置：心跳间隔 ≤ 25s，或开 TCP keepalive 30s；服务端 last_seen 判定容忍一次丢包；连接表加空闲回收（超过 2×心跳间隔未见流量即关闭并记事件），回收任务本身要幂等，避免把刚重连的连接误杀。

坑 37 · 默认线程模型撑不住心跳连接数，CPU 不高但延迟飙升

  • 触发条件：自建服务端用同步阻塞 IO 或每连接一线程，默认 backlog 与文件句柄上限没调；心跳处理里带同步落库或同步写日志；连接建立时做一次同步的鉴权查询。
  • 现象：压测到 500 连接开始 accept 超时，CPU 只有 20% 但 p95 延迟从 20ms 涨到 2s；日志里大量连接被重置；重启后短时间恢复又复发，表现为周期性雪崩。
  • 怎么提前发现：(Get-NetTCPConnection -State Established).Count 看连接数；用 1000 并发心跳脚本跑 10 分钟，记录 p50/p95 与错误率；Get-Process -Id PID | Select-Object Handles 看句柄增长，句柄涨到上限即 accept 失败。
  • 处置：改异步 IO（IOCP/epoll）或连接池；心跳处理不落同步盘，改内存聚合 + 批量落库；显式调大 backlog 与句柄上限，并把连接数、队列深度、accept 错误率做成监控指标，任一越线告警。压测脚本要模拟真实心跳间隔与重连退避，纯空连接压出来的容量数字通常会高估一倍以上。

坑 38 · 日志把 LICENSE_KEY / HWID / SESSION_TOKEN 明文打全，日志本身就是凭据库

  • 触发条件：排障期为了快，把请求体整段打进日志；日志被复制到工单、聊天群、共享盘；RESULT_DIR 里的排障包被当成「样例数据」二次分发。
  • 现象：给别人看一段日志等于给出可用卡密；用户 HWID 与 token 在多个地方留存，审计时无法证明未泄露；更糟的是这些日志会进到自建服务端的测试夹具里，被反复引用。
  • 怎么提前发现：Select-String -Path "$env:RESULT_DIR\*.log" -Pattern "LICENSE_KEY|SESSION_TOKEN|HWID" | Select-Object -First 5，看是否有明文长串；抽查日志行长度是否异常（整段 body 一行几百字符即为可疑）。
  • 处置：入口统一脱敏（卡密保留前 4 后 4、HWID 只留前 8 位 + 短哈希、token 只留 sid）；原始值只进加密审计表；日志分级，debug 级别只在本地开启并在打包时剔除；排障包生成脚本自带脱敏步骤，人工复制不再被允许。

坑 39 · 证书链不完整 / 强制 h2：curl 通，客户端握手失败

  • 触发条件：自建服务端只装叶证书没带中间证书，或只开 HTTP/2；客户端用老版本 OkHttp/WinHTTP，不认新链或不支持 h2 优先；证书 SAN 只写了域名没写 IP，本地直连 IP 时校验失败。
  • 现象：curl 一切正常，客户端报 SSL handshake failed 或 421；浏览器打开正常（会自动补链），于是误判「证书没问题」；换成 IP 直连又出现另一种失败，两个问题叠在一起。
  • 怎么提前发现：openssl s_client -connect SERVER_HOST:443 -showcerts 数证书条数（正常应 ≥2）；curl --http1.1 与 curl --http2 各打一次对比；抓 ClientHello 看 ALPN 列表；再核对证书 SAN 是否覆盖实际访问名。
  • 处置：服务端配完整链（叶 + 中间），ALPN 同时开 h2,h1；老客户端保留 h1 回退；证书 SAN 同时写域名与测试用 IP；把「客户端实际握手成功」作为验收项，不看浏览器，也不看本机 curl。抓不到 ClientHello 时先确认客户端连的域名是不是你以为的那个——hosts 与客户端内置表可能同时在起作用。

八、验证与假成功（4 条）

坑 40 · 假成功一：curl 看到 200 就宣布通了

  • 触发条件：验收判据是「HTTP 200」，不看 body 里的 code，也不看客户端是否真的消费了响应；测试脚本只断言状态码，没有产物断言。
  • 现象：自测全绿，客户端仍卡在 L3 登录窗；或登录过了但拉到的 CFG_BLOB 是 0 字节，客户端静默回退默认配置、功能全灰；此时团队开始怀疑客户端，其实服务端从第一步就错了。
  • 怎么提前发现：判据换成三件套——「客户端进入主界面 + CFG_BLOB 非空 + CRC 通过」；curl -s -o CFG_BLOB.bin -w "%{http_code} %{size_download}\n" "http://SERVER_HOST/cfg"，两个数都要看，只有状态码没有意义的场景一律补第二判据。
  • 处置：写一个 smoke 脚本串完整链路（登录 → 拉配置 → 心跳 → 指令 ACK），断言落在产物上：RESULT_DIR 里 cfg 的大小、CRC、能否被客户端同款算法解开；把「200 即通过」的旧脚本删掉，避免有人继续用它下结论。

坑 41 · 假成功二：只测登录，不测心跳与到期

  • 触发条件：测试用例止于「登录成功拿到 token」，没跑满 3 个心跳周期，也没有跨日/到期用例；环境只在本地时区测过，没测 UTC 边界。
  • 现象：演示时一切正常，用户挂机 1 小时后被踢；到期当天不踢、第二天才踢；扣时总量与账本对不上，但单次登录测试永远通过，于是问题被归为「偶发」。
  • 怎么提前发现：跑 2 小时浸泡测试，每 5 分钟采样一次「客户端剩余时间 / 服务端账本 / 在线状态」，三者画一条曲线看是否分叉；构造一张 3 分钟后到期的卡跑一次真实到期，看拦截时机与文案。
  • 处置：回归用例固定覆盖三类——至少 3 个心跳周期、一次跨日结算、一次真实到期；扣时总额用流水求和比对，差额 > 1 秒即失败；把浸泡测试做成 nightly，失败时自动保留 PCAP_FILE 与两端日志。

坑 42 · 假成功三：单机自测通过，多开与顶号逻辑没测

  • 触发条件：只有一台测试机、一个客户端实例；顶号、并发绑定、重复扣时全靠读代码推断；并发用例被当作「理论上不会发生」跳过。
  • 现象：上线后同一卡密在两台机器上互踢；并发登录把绑定关系写坏（两台都显示已绑定，或都没绑上）；扣时被扣两次；问题只在真实用户的多设备场景出现，内部永远复现不了。
  • 怎么提前发现：同一 LICENSE_KEY 起 2 个实例（同机不同目录）、不同 HWID 起 2 台机器，观察 5 分钟内的登录序列与扣时总量；并发发 10 个登录请求，看绑定表最终状态是否只有一条。
  • 处置：并发用例进回归；绑定与顶号加行锁或 Redis 锁，扣时按流水核对总额；把「两台机器同时在线」定义为必须被拒绝的状态，并断言拒绝原因码为 MSG_FORCE_LOGOUT 而不是通用失败——原因码错了，客户端重连策略就会错。多开测试要在同一台机器上跑两个独立目录，模拟真实用户「大号小号一起开」的场景；跨机测试容易漏掉同 HWID 的冲突分支。

坑 43 · 假成功四：抓包有响应，但客户端用的是缓存

  • 触发条件：客户端本地缓存带 TTL 或 cfg_rev 比较，响应到了但被判定「不比本地新」而丢弃；抓包位置在客户端侧，看到 200 + 完整 body 就以为生效。
  • 现象：改了服务端配置客户端毫无变化，误判「服务端没下发」；反复重启客户端才偶尔生效；抓包证据反而加固了错误结论，排查方向彻底跑偏。
  • 怎么提前发现：清空客户端 cache 目录再测一次；在响应里塞一个唯一标记（cfg_rev 递增 + 一个随机 NONCE）并在客户端 debug 输出里读出来，看它是否被采用；对比缓存文件 mtime 与响应时间，若 mtime 未变即命中缓存。
  • 处置：每次配置变更必须递增 cfg_rev，客户端落盘带 rev，只在新 rev 更大时覆盖；测试以「清缓存后的行为」为准，并把「清缓存」写进验收脚本第一步；灰度和回滚都靠 rev 单调性保证，不靠人工清目录。

九、跨目标的元教训

  1. 凡是客户端会静默吞掉的字段，都必须用下游产物判成败。 上游的 200、code:0、日志里的「success」都只是意图；真正的事实是 CFG_BLOB 的 CRC、注入是否成功、剩余时间是否被扣。判据永远下沉一层，下游产物比上游字段诚实。
  2. 先证明客户端真的发出了这个请求，再证明服务端回对了。 顺序反了，就会把 pinning、熔断、驱动降级这类客户端问题当成服务端 bug 修一整天；「没有请求」和「请求失败」是两类完全不同的故障，混在一起查必然误判。
  3. 服务端 UTC 墙钟是时间账本的唯一权威，扣时挂在心跳上。 客户端时间只用于展示与异常检测；剩余秒数与到期时间同时下发，靠心跳 ACK 持续纠偏。任何让客户端参与账本运算的设计，都会在改时间、挂起恢复、跨时区这三件事上被逐个击破。
  4. 每个可变状态都要有幂等键与显式状态机。 订单、指令、绑定、扣时流水——重放与重试是默认存在的（网络会重发、卡盟会重推、代理会双击）。缺状态机的系统在第一次重试时就出错，且错得静默，等到对账才发现已经多发了若干张。
  5. 配置以 (game_ver, CLIENT_VER, CHANNEL) 三元组为版本单元，禁止跨代拼装。 offsets、feature code、更新包、渠道分支必须同代同源；三元组缺失时拒绝下发，比回落到默认值安全一个数量级——默认值往往正好是「能跑但跑错」的那一代。
  6. 还原顺序固定为：客户端副产物 → 切帧 → 解业务 → 写服务端。 日志/缓存/字符串先给出字段与格式，dumper 再证明帧结构，最后才写业务逻辑。跳过前两步直接写服务端，返工成本最高，且返工点往往藏在「看起来已经通了」的地方。
