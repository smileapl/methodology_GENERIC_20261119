用法：打印一张，每轮开工前从 P0 扫到 P11；格子填不上，就不许进下一阶段。

一、主表：从零到可维护（十二阶段）

#阶段做什么判据（唯一可信）常见失败
P0分诊按 L0–L5 给客户端分层：判清哪一层是 native、哪一层是驱动或内核模块、哪一层只是脚本与配置；再把抓到的每条连接标成「登录 / 授权 / 配置 / 更新 / 心跳」，找出真正承载授权与配置的那一条，并记下它由哪一层代码发起能写出一句话：「承载 SESSION_TOKEN 与 CFG_BLOB 的连接 = 协议类型 + 端口 + 首帧方法名」；并且手动断掉这条连接后，客户端确实停在卡密窗、不再进入注入，L2 的 hook 没有 OFFSETS_TABLE 也不报错——三件事同时成立才算分诊完成一上来先解 TLS，解不开就下结论「没有业务流量」；把更新分发的连接误当授权连接；只看 UI 提示、不看连接归属；把 L1 驱动的自有通道漏掉
P1样本与静态面在 CHEAT_CORE 及其 loader 里搜加密与签名常量（S-box、HMAC 初值、SIG_KEY 派生片段、域名表），不按函数名找；把域名列表与备用列表整段提出来并统计交叉引用次数；核对二进制代次（CLIENT_VER、CHANNEL、文件 mtime、导入表）至少 1 个常量在样本里 16 字节逐字节命中，且该常量能对 CAP_FILE 里同一段密文复现出相同结果；域名列表里的每个主机名都能在抓包里找到对应的 SNI 或 Host，且分得清哪一个是 API_BASE拿磁盘上被加壳的空壳文件当分析样本；跨代搬偏移；把更新分发的域名当成 API_BASE；只看函数名不看常量；把签名常量与密钥常量当成同一个
P2抓包与解密选拦截层（系统代理 / WSS 帧级 / 驱动之前的 socket / 自研 TCP 的字节流重组），在密钥生成点做只读有界 hook 取密钥，取到后 latch 常驻不卸载；落盘为 jsonl，每行固定含 ts、conn_id、dir、method、body_len、body，密钥取点要早于第一次加密、晚于密钥派生落盘文件里 MSG_LOGIN_OK 那一行的 body 能解出可读字段，SESSION_TOKEN 长度固定，且把它重放一次仍能换到同一账号状态；同时 PCAP_FILE 与 jsonl 的行数比落在 0.9–1.1 之间；解密后的消息表非空只落索引字段不落 body，密钥丢了才想重 dump；用 push 形态（offset 0 或 4）的 hook 当取密钥点；解出空结构还继续往下走；在密钥派生之前挂 hook，拿到的是中间值
P3端点契约建模建端点表：METHOD + 路径 + 方向 + 必填字段 + 可选字段 + 错误码；把字段映射到业务语义（LICENSE_KEY、HWID、CLIENT_VER、余额、到期时间）；建错误码字典，至少覆盖 MSG_AUTH_FAIL 的全部子码；算 c2s/s2c 配对率端点表里每个被客户端真实调用过的端点都有至少 1 组 c2s 与 s2c 配对；未配对端点单独成列且数量不超过端点总数 10%；配对率与错误码覆盖率都写成算式（分子 / 分母），而不是「大部分」「基本都通」只建 c2s 表，方向一栏空着；把字段名当语义（v 可能同时是版本、签名、渠道）；未命名端点不量化就写「已还原」；把错误文案当错误码
P4授权账本还原卡密模型（计时卡 / 包月 / 永久 / 试用）、扣时发生的端点、顶号策略、冻结与解冻、退卡与补偿；账本固定三列「总量 / 已用 / 到期」，并写出可代数的对账公式用 3 张合成 LICENSE_KEY 走完「激活 → 心跳 3 次 → 到期 → 再登录被 MSG_AUTH_FAIL 拒绝」，本地账本剩余秒数与服务端返回的到期时间差不超过 1 个心跳间隔；三张卡的扣时曲线各不相同且可解释把扣时点放在登录而不放在心跳；断线重连时重复扣时；只测永久卡不测计时卡，等于没测账本；把到期时间只存在客户端本地
P5配置与更新拆 CFG_BLOB 的层次顺序（加密 → 压缩 → 编码，或相反的排列）、摸清内部 schema 版本；确认 OFFSETS_TABLE 与 CLIENT_VER 的同代约束；还原强制更新判定（force 与 ver_new 谁说话）；登记灰度键取值枚举与回滚开关自建服务端下发的 CFG_BLOB 被客户端接受后，用 OFFSETS_TABLE 里任一偏移读内存得到的值与预期一致；把 CLIENT_VER 调低一格，客户端走 MSG_UPDATE_AVAIL 而不是静默失败；改一个字节的配置被 CRC 拒收层次顺序猜反（先解 base64 再解 gzip）；偏移表跨代复用；只改 force 不改 ver_new，老客户端一直提示更新；灰度键写成布尔而不是枚举
P6心跳与指令定心跳间隔、超时、重试次数；还原强制下线（顶号 / 封禁 / 到期）三条触发；建指令队列（下发 / 拉取 / 确认 / 重放），指令带 seq 与 ack；保证幂等同一 SESSION_TOKEN 在两处登录时，先登录的一方在 1 个心跳周期内收到 MSG_FORCE_LOGOUT，其后任一请求返回 MSG_AUTH_FAIL；同一条指令重发 3 次，客户端只在第一次产生状态变化，ack 只回一次心跳只测「有回包」不测扣时；指令没有确认导致丢指令；重发导致重复执行；超时参数写死在代码里；把 MSG_HEARTBEAT_ACK 当扣时成功的唯一证据
P7卡盟对接还原四个接口：发卡、查卡、回调、结算；确认签名算法（排序拼接 + SIG_KEY）与 REPLAY_TS、NONCE 的时间窗；建三向对账（发卡平台 / 回调记录 / 本地授权库）用 CARDMALL_API 的本地桩发出一张卡，10 秒内本地授权库出现同一 LICENSE_KEY 且状态为未激活；同一 NONCE 的回调重放第二次被拒，且返回码与首次不同；三向记录的张数差为 0只做发卡不做回调；签名拼接按字母序而实际按参数出现序；不验时间窗，重放可无限次通过；把卡密当金额
P8环境断言三项断言：配置回读（服务端实际读到的键值对）、开关透传（在真正使用它的那个函数里打 gate 日志）、路径生效（起服第一条日志宣告用的是哪份文件）；任一项没有打印证据，本轮结果直接作废三项各有可打印证据：回读的键值对逐项列出、gate 日志出现 gate key=… 行、起服首行含绝对路径与文件字节数；三项齐全后，再做一次「把开关设为 0」的反证，输出必须不同env 单向覆盖配置文件且白名单漏键；改的是另一棵目录树上的副本；只看「启动成功」不看「用了哪份配置」；gate 日志打在成功分支之后，零方差
P9最小可验证切片一次只动一条链路（先登录、再授权、再配置、最后指令）；先建状态再发增量；先定构造源（客户端实体来自哪一帧：登录回包 / 配置推送 / 指令下发）再谈注入每轮只变一个变量，下游产物（UI 文案 / 注入成功标志 / 内存偏移值 / 账本数字）在改动前后可区分；负对照的产出与正例明显不同；构造源一致时同一实体只出现一次一轮同时改三个变量；把增量推到客户端并不存在的容器；用运行时属性去改由回放帧构造出来的实体；只改 UI 文案就宣布生效
P10全链路闭环登录 → 授权 → 拉配置 → 注入 → 运行 → 心跳 → 到期，一条动作从头走完，逐环节记录 c2s/s2c 与状态变化，并跑一遍 3 × 3 回归矩阵从输入 LICENSE_KEY 到游戏内生效再到到期拦截全程无人工干预，7 个环节各有至少 1 条 s2c 证据，且回归矩阵里 3 个 CHANNEL × 3 个 CLIENT_VER 的登录、配置、心跳三项全绿用管理命令绕过状态机造成假闭环；中途手动改库；只验最后一步，前面全靠推断；把一次成功当成矩阵通过
P11可维护建代次账簿（哪一版 CLIENT_VER 配哪一版 CFG_BLOB 与 OFFSETS_TABLE，四列齐全）、偏移迁移五步、协议变更四类探测（字段增 / 字段删 / 字段号变 / 顺序变）、三份快照（代码 / 数据 / 协议）、部署拓扑换上一代 CLIENT_VER 的样本后，P2–P6 的判据仍全绿，并且代次账簿里能查到这次迁移用的锚点与结构化 diff；断网一小时后再起，能按账簿恢复到同一套配置偏移硬编码；备份靠扩展名过滤去找；没有代次账簿，每换一版都从零开始；只有一份快照，改了代码就丢了当时的配置

二、专项清单 A：授权与时间账本

  • &#9744; A01 三种计费形态：计时卡按秒递减、包月卡按天递减、永久卡不产生任何扣时流水——同一 LICENSE_KEY 的三次合成开通，三条扣时曲线彼此可分，且都能用账本三列复算出来。
  • &#9744; A02 扣时端点唯一：扣时只发生在 MSG_HEARTBEAT_ACK 对应的那一个端点；抓包里「扣时请求发出」与「账本数字变小」的时间差不超过 1 秒，不存在第二条偷偷扣时的路径；把该端点返回改成业务码非 0，账本必须一分不动。
  • &#9744; A03 断线保底：客户端断网 120 秒后恢复，账本剩余时长与断网前完全一致，误差 0 秒；断网期间不产生任何扣时流水，恢复后也不补扣。
  • &#9744; A04 顶号策略写明：同 HWID 二次登录是否顶掉、不同 HWID 是否直接拒绝、被顶方是否收到 MSG_FORCE_LOGOUT——三种情形各有一条实测记录，且被顶方不会短暂地继续注入。
  • &#9744; A05 并发会话上限：同时 2 个会话时第 3 个被拒，拒码在错误码字典里能查到，且客户端 UI 文案与该码一致，不出现「提示成功但进不去」。
  • &#9744; A06 HWID 更换次数：同一 LICENSE_KEY 第 N+1 次更换 HWID 被拒；改回原值可恢复；计数存在服务端，清空本地配置与重装客户端后仍然生效。
  • &#9744; A07 试用与赠送：试用卡只能激活一次，重复激活返回可识别错误码；赠送时长进入账本流水，且不重复计入对账公式，赠送到账时间可查。
  • &#9744; A08 冻结 / 解冻：冻结期间心跳返回 MSG_AUTH_FAIL 且不扣时；解冻后剩余时长与冻结前逐秒一致；冻结存量与解冻存量在账本里各有一列。
  • &#9744; A09 退卡与补偿：退款后卡状态为已退，重新激活被拒；补偿只增加时长、不改变卡状态，两件事在流水里分列，金额与时长不互相折算。
  • &#9744; A10 时区与时钟漂移：服务端与客户端时区不同、客户端时钟分别前偏与后偏 10 分钟，到期判定仍以服务端时间为准，客户端自己的倒计时只是显示。
  • &#9744; A11 账本对账：发卡总量 = 已激活 + 未激活 + 已退款 + 已冻结，四项相加与发卡总量之差为 0，公式可直接套在导出的流水上，换一段时间窗仍成立。
  • &#9744; A12 审计留痕：每次扣时、冻结、顶号、退款都记 actor、REPLAY_TS、旧值 → 新值三列，且可以按 SESSION_TOKEN 反查到是哪次登录触发的。
  • &#9744; A13 到期边界那一秒：剩余 0 秒的同一秒内，注入链路断开、UI 出到期提示、请求被拒三件事的先后顺序固定且可复现，重复 10 次结果一致。
  • &#9744; A14 重放保护：同一 NONCE 的登录或扣时请求第二次被拒，并且不产生第二条扣时流水；把 NONCE 改成随机值后才通过。
  • &#9744; A15 时间基准单钟：账本只认服务端写入的 REPLAY_TS，客户端上报的时间只作为偏移量参考，不参与到期计算，改本地时间不改变剩余时长。
  • &#9744; A16 异常路径：心跳返回 MSG_AUTH_FAIL 但本地仍显示余额时，客户端的行为（继续尝试 / 退出 / 静默降级）已实测并记录，三种行为各有抓包证据。
  • &#9744; A17 心跳与扣时解耦：心跳只证明在线，扣时由独立定时器驱动——停发心跳 60 秒后账本仍按秒递减，恢复心跳后不补扣那 60 秒。
  • &#9744; A18 卡密格式：LICENSE_KEY 的长度、字符集、校验位规则已记录，格式错的卡号在客户端本地就被拒，根本不落到服务端。

三、专项清单 B：配置与更新下发

  • &#9744; B01 层次顺序先证后拆：把 CFG_BLOB 在三个候选顺序里各解一次，只有一种能得到可解析结构，另外两种必须失败——失败也要留证，否则等于没有排除。
  • &#9744; B02 密钥与 IV 来源：确认 SIG_KEY 是硬编码、运行时派生还是随包下发；IV 是固定、随包携带还是由 NONCE 派生，四者组合只有一种能解出明文。
  • &#9744; B03 内部 schema 版本：改 CFG_BLOB 内部版本字段一位，客户端必须拒绝并给出可观测错误，而不是静默按旧结构解析出一堆空值。
  • &#9744; B04 同代约束：把上一代 OFFSETS_TABLE 配给新一代 CLIENT_VER，客户端要么拒收，要么读出的偏移值明显错误——两者必居其一，且已实测记录是哪一种。
  • &#9744; B05 特征码自校验：客户端对 CFG_BLOB 做 CRC 或长度校验，改动其中 1 个字节即被拒收；校验失败时的错误路径（重拉 / 降级 / 停用）可复现，并确认被拒的是校验而不是签名。
  • &#9744; B06 增量与全量：先下全量再下增量；增量包缺基线时客户端回退到全量，回退行为在抓包里能看到两次请求，且最终配置版本正确。
  • &#9744; B07 强制更新字段名：写清 force 与 ver_new 谁说话；两者矛盾时（force=1 但版本已够、force=0 但版本不够）客户端实际走哪条分支，各做一次构造。
  • &#9744; B08 灰度键：CHANNEL 或灰度键决定下发哪一版配置，切换键值后 30 秒内生效，且灰度用户与全量用户的 CFG_BLOB 版本号不同且可分别查。
  • &#9744; B09 回滚开关：只改开关、不动 CFG_BLOB 本身，就能把客户端退回上一版可用配置；回滚后注入仍能跑通，偏移表仍同代。
  • &#9744; B10 分发缓存与带宽：CFG_BLOB 与更新包的缓存头、ETag、断点续传是否被客户端真的用上；三次重复拉取里缓存命中几次，命中时是否仍校验版本。
  • &#9744; B11 签名失败降级路径：签名错时客户端是拒收、忽略还是回退上一版——三种行为各做一次构造，记录实际走哪一条以及回退后的版本号。
  • &#9744; B12 落盘回读：下发的 CFG_BLOB 在客户端落盘位置、文件字节数可回读，且与内存里的版本号一致；重装客户端后能从落盘文件恢复。
  • &#9744; B13 版本单调：更新包的 CLIENT_VER 单调递增，降版本安装被拒；越过中间版本的跨代安装行为已实测，失败时提示的是哪一句。
  • &#9744; B14 下发成功率口径：100 次下发里的失败数与失败码分布逐项列出，分母是「请求数」而不是「会话数」，两者同时给出以免口径混淆。
  • &#9744; B15 配置与偏移表一致性：CFG_BLOB 里声明的偏移条数与 OFFSETS_TABLE 实际条数相等，任一条缺失都能被客户端发现，而不是静默少注入一个 hook。
  • &#9744; B16 本地配置复用：客户端重启后是否复用本地 CFG_BLOB，复用条件是「版本号一致 + 未过期 + 签名有效」三者的哪一个组合，已实测。
  • &#9744; B17 更新断点续传：更新包下载到一半断开，重连后从断点继续而不是从头下载，且最终文件哈希与完整下载一致。

四、专项清单 C：协议逆向与假成功识别

  • &#9744; C01 HTTP 200 但业务码非 0：所有 200 响应逐条读 body 里的业务码，禁止按 HTTP 状态码统计成功率；统计表里必须同时有 HTTP 分布与业务码分布。
  • &#9744; C02 空 body 但 Content-Length 非零：说明外层还有包装层，先看原始字节再谈解析，否则会得出「服务端返回空」的错误结论并据此改坏服务端。
  • &#9744; C03 签名顺序：排序拼接 + SIG_KEY，排序按字母序还是按参数出现序，用两次改序请求复现出唯一正确的那种，错的那种必须被拒。
  • &#9744; C04 时间戳窗口与 NONCE：REPLAY_TS 超出窗口被拒、同一 NONCE 二次被拒；窗口大小用边界扫描测出（前后各扫 1 个数量级），而不是猜 30 秒；客户端与服务端时钟不同步时，被拒的是时间戳而不是签名。
  • &#9744; C05 TLS pinning 绕过点：定位到具体校验函数，并验证「绕过之后能通」，而不是「改了之后没崩」；两条握手路径（HTTP 与 WSS）分别验一次。
  • &#9744; C06 gzip 与 AES 先后：拿一段同时压缩又加密的样本，两种顺序各解一次，只有一种出明文，另一种必须报错，报错信息也要记录。
  • &#9744; C07 字段名不是语义：v 可能是版本、签名或渠道，用值域、变化频率与出现位置三件事定名，命名后写进端点表并注明依据。
  • &#9744; C08 双端编码差异：hex 与 base64 可能在同一字段的 c2s 与 s2c 里不同，两个方向分别验一次；不一致时以能解析出已知明文的那一侧为准。
  • &#9744; C09 错误码字典覆盖率：客户端能触发的错误码里有字典解释的比例，未覆盖的逐条列出并标注「未知」，未知项数写进当轮报告。
  • &#9744; C10 未命名端点量化：数量、调用次数占比、是否有对应 s2c 三项齐全；缺任一项就不算「已还原」，只算「已观测」。
  • &#9744; C11 假成功两型：心跳有回包但账本没变 = 未扣时；注入日志有输出但游戏内无效果 = 未生效，两类分开记，不许合并成「部分成功」。
  • &#9744; C12 成功标志与状态同向：响应体里的成功标志必须与后续状态变化同向；只有标志没有状态变化的一律记为假成功，并从成功计数里剔除。
  • &#9744; C13 WSS 帧头不是业务字段：帧级抓包里多包的那一层（帧类型、长度、掩码）不要当业务字段写进端点表，否则字段数会凭空多出一倍。
  • &#9744; C14 自研 TCP 的粘包边界：用 body_len 与下一帧首字节验证分包，不靠猜分隔符；重组失败的行单独统计，失败率高时先怀疑长度字段的字节序。
  • &#9744; C15 负对照常备：每类判据都要有一个「已知失败」的样本，它的产出必须与正例不同；若两者相同，判据本身作废而不是结果作废。
  • &#9744; C16 双端字段数量差：同一端点在 c2s 与 s2c 的字段数量往往不同，缺的字段是服务端补的还是客户端根本不发，逐字段标注，别按对称结构假设。
  • &#9744; C17 编码探测顺序：先判二进制魔数（gzip、zip、自定义头）再判文本编码，避免把压缩头当 base64 解出一段垃圾还当成加密。

五、专项清单 D：环境与工程纪律

  • &#9744; D01 二进制与源码同代：CHEAT_CORE 及其 loader 的文件 mtime 晚于所有改动过的源码，否则测的是旧程序；哈希不同而 mtime 相同时，以哈希为准。
  • &#9744; D02 单一执行者互斥：同一时间只有一个客户端实例、一个抓包器、一个服务端进程动同一份授权库；换人接手前先确认前一个进程已退出。
  • &#9744; D03 env 不残留：每轮从干净环境起，env 里的开关与配置文件里的值一致；不一致时以回读值为准，并把差异记进当轮清单。
  • &#9744; D04 正确的那棵目录树：改动前打印绝对路径、文件字节数与哈希三项，确认动的是权威副本而不是备份副本或上一轮的缓存目录。
  • &#9744; D05 改前备份：备份名带轮次后缀，恢复时按名字找，不按扩展名过滤去找；备份与原件放在不同目录。
  • &#9744; D06 同一时钟：客户端日志、服务端日志、PCAP_FILE 三者时间基准一致；跨钟相减得出的延迟不采信，只用于看顺序；确有偏差时先量出偏差量并记录，再决定是否校正。
  • &#9744; D07 危险动作红线：改域名、DNS、证书前先确认可回滚；自建服务端只在本地 hosts 或代理层生效，不动线上解析，也不改系统证书库。
  • &#9744; D08 产物目录规范：RESULT_DIR 下按轮次分目录，CAP_FILE、PCAP_FILE、解密 jsonl 三类产物每次齐全，文件名带阶段号。
  • &#9744; D09 扫描边界：只在密钥或状态生成点做只读有界 hook，不做全堆扫描、不对高频热函数长期挂载，避免把观测动作本身变成风控触发条件。
  • &#9744; D10 启动即记账：每次启动记下 CLIENT_VER、文件哈希、启动时间，三者写进当轮目录的清单文件，供后续分期统计使用。
  • &#9744; D11 密钥不落明文：SIG_KEY、SESSION_TOKEN 在日志里只记长度或指纹，不记原文；截图与录屏同样按此处理。
  • &#9744; D12 失败也留证：失败轮次的抓包、日志、配置快照同样归档，否则无法做「改前 / 改后」对照，失败会变成无证据的传闻。
  • &#9744; D13 单变量原则：一轮只改一个开关或一个字段；需要同时改两处时，先加一次中间验证轮，确认第一处单独生效。
  • &#9744; D14 参数外置：心跳间隔、超时、重试次数写在配置文件里而不是代码里，改参数不需要重新编译，也不需要重新签名。
  • &#9744; D15 端口与实例隔离：自建服务端与对照用的桩服务不共用端口，端口冲突时以起服日志里的绑定结果为准，不看命令是否返回 0。
  • &#9744; D16 日志按轮切分：单轮日志超过阈值时按轮次切分，避免把两轮日志混成一个文件后无法分期统计。
  • &#9744; D17 只读原则：取密钥与读状态的 hook 一律不写内存；确需写入时单独开一轮，并保留写前写后两份快照。

六、专项清单 E：上线与容灾

  • &#9744; E01 多域名轮询：主域名不可用时客户端在既定秒数内切到备用列表里的下一个，切换动作能在抓包里看到两次连接，切换耗时已记录。
  • &#9744; E02 证书与域名匹配：自签证书的 CN / SAN 覆盖客户端实际校验的字段，否则连 pinning 都还没到就断在握手，日志里只看到 EOF。
  • &#9744; E03 健康检查端点：一个不依赖授权库的 /health 返回 200，body 里带服务端版本号与启动时间，数据库挂掉时它仍返回 200。
  • &#9744; E04 限流与防刷：单 HWID 每分钟登录次数超限时返回可识别错误码，正常用户在同窗口内不受影响，限流阈值可配置。
  • &#9744; E05 备份与恢复演练：从备份恢复后，账本对账公式仍成立（差值为 0），并记录恢复耗时与丢失的最后一条流水。
  • &#9744; E06 灰度渠道：CHANNEL 分流比例可调，灰度用户与全量用户拿到的 CFG_BLOB 版本号不同，回退比例也能调。
  • &#9744; E07 监控四指标：登录成功率、心跳存活率、配置下发 200 率、指令到达率，四个都有基线与告警阈值，且口径写在看板标题上；基线取上线后同时间段（如连续 3 天 20:00–23:00）的中位数，而不是上线首小时的平均。
  • &#9744; E08 回滚演练：服务端回退一版后，老客户端仍能登录并拉到上一版 CFG_BLOB，注入不受影响；回滚脚本本身跑过一次。
  • &#9744; E09 容量与降级：并发会话达到上限时的行为是排队还是拒绝，写清楚并实测一次，排队时的超时与提示文案一并记录。
  • &#9744; E10 灾备两态：授权库丢失后，客户端是停在卡密窗还是继续用本地缓存的 SESSION_TOKEN——两种都要实测，并据此决定备份频率；备份间隔按「最坏损失」倒推，而不是按惯例设成每天一次。
  • &#9744; E11 备用通道：HTTP(S) 与 WSS 两条通道至少各有一条可用；一条被阻断时另一条能在既定时间内接管，接管过程不掉会话。
  • &#9744; E12 时钟同步策略：服务端与客户端时间差超过阈值时客户端是否被拒——行为已记录，阈值可配置，不因一次漂移就把所有用户踢下线。

七、每次开工前的 8 项自检（缺一项 ⇒ 结果作废）

□ 1 代次    CHEAT_CORE 的哈希与 CLIENT_VER 已记录，与上一轮是同一代还是新一代，能一句话说清？
□ 2 配置    自建服务端回读到的键值对与预期逐项一致，且打印在起服首行？
□ 3 基线    待改的每个端点都有一组上一轮的 c2s / s2c 基线可以对比？
□ 4 负对照  本轮跑了一组「已知失败」的样本，它的产出与正例确实不同？
□ 5 路径    日志第一条宣告「我用的是你指定的那份 CFG_BLOB」，含绝对路径与字节数？
□ 6 干净    没有第二个执行者在动同一份授权库，env 不是上一轮残留？
□ 7 判据    本轮的判据写成了一句可观测的话，并写下「不成立时我会看到什么」？
□ 8 可归属  失败时我能区分「没下发」和「下发了但客户端没用」？

★ 第 8 项最常被跳过，也最值钱。没有它，失败就会退化成「再来一轮」的循环。

八、报任何数字之前的 5 项检查

  1. 口径是否分期：按 CLIENT_VER 与服务端版本的变更时间分期；跨代混算等于把历史平均当现状，数字越漂亮越可疑。
  2. 是否去重：同一心跳或同一指令的重发记录先按 NONCE + REPLAY_TS 去重，否则成功率被重复样本稀释，失败率被放大。
  3. 样本量是否够报：确定性判据 1 次即可；比例类（登录成功率、下发 200 率）至少 100 次请求并给出区间，低于 30 次只报「样本不足」；同一指标在两次采样之间的波动也要给出，否则分不清改善与噪声。
  4. Δ 是否给出：每个数字都要配「正例 − 负对照」或「改前 − 改后」，没有 Δ 的绝对值不报；Δ 为负时同样照报，不许沉默。
  5. 是否区分「没生效」与「生效了但没用」：前者看 gate 日志与下发记录，后者看下游产物（游戏内效果、账本变化），两者混在一起会得出相反结论。

九、什么时候停手（三条硬停手）

  1. 判据不成立却想改结论：换尺子必须有独立的新证据（新的可观测现象、另一条不共享血缘的数据路径），不能因为结果不合预期就改判据；例如把「登录成功」从「收到 MSG_LOGIN_OK」改成「token 能换来 CFG_BLOB」，理由必须是前者在失败场次里也为真，而不是成功数太少。
  2. 只能靠「感觉」解释差异：说不出是哪一行日志、哪个字段、哪一次请求造成的差异，就停下来补采集，不要往下推，也不要先改代码再看。
  3. 需要动生产环境才能继续验证：一旦要改线上域名、线上库、线上证书，就停，改用本地桩与代理层复现；能复现的才叫验证，不能复现的只是猜测。桩的合格标准是：把端点换成本地桩后，同一动作能复现同一组 s2c 与同一条状态变化。
